# Octoboard UI

`@octoboard/ui`: a HeroUI 3 + React 19 + Tailwind 4 + Vite application, the UI of the desktop application. The macOS
shell in [`../../apps/desktop/`](../../apps/desktop/README.md) loads this package's `dist/` (bundled into the
application, not served by the daemon), and the same build also runs in a plain browser. It has the window chrome (a
top bar across the window and a left rail), the content panel under it holding the sidebar, the terminal pane and the
aside (a console session's report panel or a project's browser, its files, its worktrees' uncommitted changes and a
comparison of two local branches) — or, while the daemon has no console, a welcome screen alone in their place — the
archive view, the dialogs and the settings dialog, toasts and the failure screens, all in the user's language (see
`src/i18n/` below).

It talks to `octoboardd` (see [`../../apps/daemon/`](../../apps/daemon/README.md)) only over the WebSocket protocol in
[`../../apps/daemon/PROTOCOL.md`](../../apps/daemon/PROTOCOL.md), and reaches anything native (quit flow, system
notifications, Dock badge, the native window's own theme, the window chrome, the app menu, the menu bar icon, the macOS privacy grants) only through the platform
adapter, which is chosen once at startup. The separate website-preview entry renders the same `App` over local
fixtures for the public website, without a live daemon connection.

## Development

This is a package of the repository's pnpm workspace: install from the workspace root with `pnpm install`, then run
the scripts from this directory.

- `pnpm dev` — the Vite dev server on port 5174, which is also what `pnpm tauri dev` in `apps/desktop/` starts and
  opens its window on.
- `pnpm gallery` — the same dev server on port 5175, opening the UI state gallery (below) in the browser.
- `pnpm gallery:sweep` — loads every gallery scenario in a headless browser and fails on any gallery failure (see
  "Sweeping the gallery" below).
- `pnpm typecheck` — `tsc --noEmit`.
- `pnpm test` — `vitest run`: the unit tests beside the code (`*.test.ts`), for the pure modules, plus jsdom tests for stateful classes and components (`*.test.ts`, `*.test.tsx`).
- `pnpm build` — typechecks, runs the catalog check (`vitest run src/i18n`), then writes `dist/` with relative asset
  paths, so a static server or a shell can serve it from any path. Opening `dist/index.html` over `file://` does not
  work: Chrome refuses module scripts from a `null` origin.
- `pnpm build:preview` — builds the standalone website demonstration into `apps/web/public/preview/` using
  `vite.preview.config.ts`; the website's development and generation commands invoke it.

### The UI state gallery

The dev server serves a dev-only gallery of states that are hard to reach against a live daemon at `/gallery.html` (no
daemon needed): `pnpm gallery` serves it on port 5175 and opens it, and under `pnpm dev` it is at
`http://localhost:5174/gallery.html`. The list is organized into functional areas, each with Normal previews first
and Exceptional previews second, with counts and an explicit label when a subsection has no previews. The selected
function, category and title remain visible above the preview. Opening without a scenario selects the normal welcome
screen; existing scenario ids remain supported for deep links. Pick a scenario from the list; light/dark, any
offered language (`ar` is the right-to-left one), the window width and the window height are controls above the
window, and all of them are in the URL, so a link reproduces a view. The window is an iframe, so its width decides the `docked` breakpoint (1148px) for
real. The real `App` renders over a fixture daemon (`src/gallery/fixtureDaemon.ts`). A scenario's page writes its
`octoboard.*` and `heroui-theme` entries into `localStorage` on every load; on port 5174 that origin is the dev app's
own, so opening the gallery there resets the dev app's preferences, which `pnpm gallery`'s port avoids. A scenario's
page sets `data-gallery-ready` on `<html>` once its steps have run and then after two frames or 200ms, whichever comes
first, which is what automation waits on before capturing (a page too busy to draw two frames in that time claims it
without them). A failure of the gallery's own machinery, a step that threw, a fixture that cannot be answered as the
real daemon would answer, or an exit transition that never ends (something that was closing is still on the page once
the steps have run; a scroll-driven animation on a settings panel did that), is painted over the page as a red
`[data-gallery-failure]` overlay (`src/gallery/banner.ts`), so a capture taken once the page is ready should be checked
for it. The fixture daemon (for the Git mode, `src/gallery/fixtureGit.ts`) refuses
such a reply rather than sending the field unfilled: where the real daemon counts a change side's `lines`, the fixture
has to carry the text to count it from (`FixtureChange.whole` in `fixtures/changeFixtures.ts`, the text of each side of
a two-sided change), or the request rejects with `FixtureUnfillableError`. A change fixture is written through the
factory for its kind of change (`textChange`, `deletion`, `untracked` and the rest in `fixtures/changeFixtures.ts`),
never as a literal, so a change the fixture daemon could not answer faithfully cannot be written. What no single change
can show, a rule over a whole repository, is held by a test over the sample repository instead: `objectIdCheck`
(`fixtures/invariants.ts`) reports where an object id names more than one content or one content is named by more than
one id, as Git's names do not, and the ids it has no content to hold the rule over; a rule of that kind is added there.
A frame URL with `chrome=1` gives the page the desktop window's `windowChrome` capability (`src/gallery/frame.tsx`), so
what only the desktop app offers, such as the window shortcuts, can be driven in a browser. Neither gallery page is part
of the bundle `pnpm build` writes, but `src/gallery/` is still type-checked by it, so a broken fixture fails the build.

Normal previews cover expected UI, including empty views, loading and platform limitations. Exceptional previews
show deliberate failures, validation errors, refusals or conflicts. Keep failed subjects out of normal navigation;
give each distinct exceptional confirmation target its own preview rather than hiding it behind a normal subject.

Each scenario presents one identifiable, settled view for confirmation. After initialization it stays there until
user interaction; autonomous behavior intrinsic to the view remains part of its subject. Share mock data across
scenarios and combine compatible cases visible together, but give distinct confirmation targets their own entries
when presenting one replaces the other. A reversible route between targets does not make them the same view.

Initialize the target with declarative state where supported; otherwise use the shortest setup that reaches it.
Setup does not tour unrelated views, return through earlier views or run regression checks. Keep behavioral
assertions in tests or separate verification runs. Additional assertions or captures do not by themselves justify
entries, and page-level viewing controls can vary the same target without duplicating it. Mock data supplies the
fields and conditions required by the target; compatible examples should not obscure what is being confirmed.

To add a scenario, add an entry to the file for its area in `src/gallery/fixtures/` (or a new file, listed in
`index.ts`); its `group` is one of the titles in `GROUPS` (`groups.ts`), where a new group gets the icon its heading
carries. Set the required `category` to `"normal"` or `"exceptional"` according to the view being confirmed, rather
than the name of its component or fixture file. Its `state` is built with `snapshotState` from the helpers in
`builders.ts`, so a protocol change breaks it at typecheck. State that lives in a component rather than the store (a dialog, the archive view, which session is selected)
is reached with the shortest `steps` needed, which press controls by name as a user would (`ui.press(ui.t("rail.settings"))`; a dialog's
confirming button, named as a control behind it, is pressed with `ui.confirm()`). `preferences` sets what the app
persists (pane visibility and widths, the sidebar's console and focus target), `toasts` raises daemon errors and
notices, `sessionOpenError` makes `open_session` refuse with a daemon error, `terminal: "refuse"` makes a session's
terminal unreachable, `clipboard: "unavailable"` takes the clipboard
away from the platform (a plain browser over insecure http, where the file, directory and change rows offer no actions
button and the file viewer's header no copy button), and `macosPermissions` stubs the desktop shell's macOS privacy
grants for the settings dialog's Permissions section (`"unreadable"` for a shell that refuses the read; without it the
page is a plain browser's, whose section says it is macOS-only). `width` is the window this page opens the scenario at,
and `height` the window height, which is otherwise the page's own. On its own, a width chosen above the window follows
you from scenario to scenario, so picking a scenario that carries its own width drops the chosen width; a link that
names both still reproduces what it names. A chosen width does stay on the scenarios that carry none, which is what
sweeping the list at one width is for — so press Wide again before reading a scenario that rests on the docked window.
The same holds for the height. The standalone frame has no width or height of its own and takes the browser window's, so
"Open alone" on a scenario that needs a narrow or a short window needs one.

A scenario is written without a `width` unless the window itself is part of it: the page opens one at 1440, so that
width is never written, and a scenario that rests on the wide window needs none. Set one where steps open a drawer,
which exists only below the breakpoint, or where the layout under test is about a single width (the tightest docked
window, the width a label starts clipping at), and say in the title or the description what that width buys. The width
controls above the window reproduce any width a scenario's steps can run at, so a copy of another scenario that differs
only by its width earns nothing. The same goes for a `height`: it is written only where a step needs the window too
short for a dialog's body, which then scrolls (`ui.tabToRegion`, which focuses that scrolling body as Tab would, finds
none in a window tall enough to hold the dialog), and a scenario that merely wants to be seen in a short window is
seen with the Short height control instead. A height needed by a step determines how that step can run; it does
not justify a duplicate target solely for its viewing condition. A distinct confirmation view may share the same
mock data and require its own minimal initialization.

A step names a control in the language the window is in, so copy is never written out: a control is named through
`ui.t` (`ui.press(ui.t("rail.settings"))`), a session row through `ui.session` and a change row through `ui.changeRow`.
A name that is not copy (a branch, a file, a title the fixture itself sets) is a plain string or a test of the name; a
matcher is never a pattern, since a pattern is written in one human language. `fixtures.test.ts` fails a step that
names a control with the English text of a message another language's catalog translates, written out bare
(`"Show whole file"`) or filled (`"new-name.ts, renamed"`); it flags a string that fits a translated message's literal
frame, whatever fills it, so a data name shaped like one (`"notes, drafts.txt"`) is flagged too. It cannot see through a
test of the name that closes over such text (`(name) => name.startsWith("new-name.ts, renamed")`): that is checked only
against the bare messages, so a test of the name that stands for copy is built from the helpers. A test of the name
that is not from a helper can be given a description with `describing(...)`, which is what a failed step reports in
place of the test's source; it changes nothing the check sees.

`configuration` is what the platform and the daemon answer to exporting and importing configuration
(`src/gallery/fixtureConfiguration.ts`). The gallery's platform always stubs the configuration-file capability, so no
download or file picker is raised from a capture: `file` is what the open dialog hands back (`"dismissed"` and
`"pending"` for one closed or never answered, `readError` for one that fails), `saveError` makes the save fail,
`downloads` makes it a browser's download, which cannot say what it was saved as, and `unavailable` leaves the platform
with no configuration-file capability at all. Exporting needs nothing given, the document being built from the
scenario's state. An inspection and an import result are written out per scenario, since they depend on the daemon's
disk and clones, and the fixture daemon refuses an import result that does not follow from what the steps asked for (a
project left out that was given a choice, one placed another way than was chosen, application settings reported without
the checkbox ticked; a console that could not be created is not looked into, its projects being not tried whatever was
chosen), while `fixtures/configuration.test.ts` holds what is written to the rules the daemon follows (what is offered
and preselected, fallbacks only for accounts the machine lacks, a result that lines up with its inspection).

#### Sweeping the gallery

`pnpm gallery:sweep` checks that selected scenarios run: their steps find controls and pass their assertions,
fixtures answer, exit transitions finish, pages become ready, and the gallery reports no rendering or setup failure.
Limit it to affected scenario ids, patterns or groups, and the languages and themes relevant to the change. For a
shared component, include every affected caller's scenarios, not just a newly added one. Run the full gallery only
when a broad change leaves the affected scope uncertain.

Do not repeat a sweep when actual browser verification already covered the same scenarios and conditions, including
the setup steps, their assertions and failure checks. Looking at the final picture alone does not cover an assertion
that ran earlier. Check mock fields and conditions against the changed component, fixture implementation and protocol
contracts; a clean sweep does not prove that a fixture represents the latest UI or that the intended state is visible.
Use browser inspection when the visual or interaction behavior needs confirmation, rather than for every data update.

The sweep starts this checkout's Vite dev server (the gallery is the dev server's unbundled modules, so it is not
swept from a build), loads each scenario's frame page, waits for
`data-gallery-ready`, gives the page another 150 ms for whatever a step did not wait for, and reads the
`[data-gallery-failure]` overlay. That pause is a fixed one: the sweep does not watch the page's requests, so a
renderer that takes longer than that to arrive after the steps ended is read before it has had its say. Each failure is
printed with the language, theme, scenario id and the banner's text, and the exit status is 1 when any scenario failed
(2 when the sweep could not run at all, 128 plus the signal's number when it was interrupted, which prints nothing about
the pages it was loading).

```sh
pnpm gallery:sweep git-badges               # one affected scenario, en and zh-Hans, light
pnpm gallery:sweep "git-*"                  # affected ids by pattern; several ids or patterns may be given
pnpm gallery:sweep --group "Project pane: Git" --lang zh-Hans
pnpm gallery:sweep git-badges --theme dark  # or "both"; --list prints the ids a selection names
pnpm gallery:sweep                         # full gallery only for a broad change with uncertain scope
```

Languages default to `en` and `zh-Hans`, the two with catalogs (the other 15 render English word for word, so sweeping
them adds loads and no coverage). `--lang` takes the app's own language tags and refuses any other, since the gallery
page would render English for it and the sweep would report that as the language it was asked for. The theme defaults to
light: a scenario's steps do not depend on it, so it settles whether a state still renders, and `--theme dark` is for a
change to colours. `--url` sweeps a gallery that is already being served (a running `pnpm gallery`) instead of starting
a server.

Pages are loaded `--jobs` at a time (default: six tenths of the cores, at most 6), each worker with a browser context of
its own, since a scenario's page rewrites the `octoboard.*` entries of `localStorage` on every load and two pages in one
context would overwrite each other's starting preferences. A failure seen under load is run again alone, to tell a
scenario that no longer runs from one that fails only while pages load together. Both fail the sweep: one that passes
alone is listed apart, as a step that races an animation or a fixture reply that races a render, which a busy machine
shows and a quiet one hides. `--jobs 1` runs the scenario with nothing else loading. At any `--jobs`, a page that was
lost rather than slow (a crashed renderer) is reported as such, not as one that never became ready.

Playwright is a devDependency of this package (pinned to one version), so `pnpm install` is all the script itself needs.
The dependency installs no browser: fetch the one that version expects with `pnpm exec playwright install chromium`, run
from `packages/ui` (from the workspace root `pnpm exec playwright` resolves to a machine-global Playwright, or to
nothing). `--playwright <dir>` / `OCTOBOARD_PLAYWRIGHT` (a directory holding `node_modules/playwright`, or the package
itself) points the sweep at another installation instead, for a machine whose Playwright browser cache holds another
version's binaries; that installation fetches its own browser with its own `playwright install chromium`. The browser is
Playwright's own Chromium, or, where that revision is not downloaded, the newest `chromium_headless_shell` in
Playwright's browser cache; `--chromium <path>` / `OCTOBOARD_CHROMIUM` names one. A browser that is present but will not
start usually wants `playwright install --with-deps chromium`. Chromium settles the same things the gallery does
everywhere (a step that ran, a fixture that answered), not WebKit rendering or a pointer interaction: those are checked
with the gallery page loaded in Playwright's `webkit`, driving the pointer through real input (that browser is fetched
the same way, with `pnpm exec playwright install webkit` run from `packages/ui`).

### Pointing it at a daemon

The daemon binds an OS-assigned port. Start `octoboardd` and read the port from the first line it prints on stdout, or
from `$TMPDIR/octoboardd.port`. Then either:

- open `http://localhost:5174/?port=<port>`, or set `VITE_DAEMON_PORT`; or
- run `OCTOBOARD_DAEMON_PORT=<port> pnpm dev` and open the plain URL, which reaches the daemon through a same-origin
  `/ws` proxy (`vite.config.ts`).

Both variables can also be set in the committed repo-root `.env` (commented out there) or a gitignored `.env.local`;
a variable in the shell wins over them. The dev server reads those files and a `vite build` never does. Prefer them to
a `packages/ui/.env`: that directory is vite's own `envDir`, so a `vite build` reads it too and a `VITE_DAEMON_PORT`
there goes into a release bundle, and vite expands `$VAR` in it where the root files are read literally.

With none of these the page shows a "no daemon address" screen. A daemon started by hand for development should get an
isolated `HOME` and `TMPDIR`: its instance lock (`daemon.lock`) and database live under `$HOME/.octoboard`, and the
port file under the temp directory, so the defaults would touch the real data and collide with a running instance.

## The file viewer

`src/viewer/` is a read-only modal that shows one subject: a file's text or image, a change between two versions, or
the loading or failed state of either. It is for the project file browser and its change views; no edit or save
interaction exists, and a file is never inserted as its own markup (a rendered document still draws a diagram or a formula from generated markup; see **Markdown**). The app reaches it
only through the project browser (`src/browser/`), which is loaded lazily; the gallery's "File viewer" group exercises it
on its own (see "The UI state gallery").

The header is the title, the file's name followed by the status chip and the stage tag, then the subtitle where the
subject has a `source` (a compared change's "from" wording, drawn by `Dialog`'s `subtitle` slot directly under the
title), then a details block: the path, the size (drawn as a chip) and a rename's origin are separate items
(`DetailItem` in `FileViewer.tsx`, the path and the origin drawn as `PlainMarkedPath` with a file icon) that flow around
the view controls, which float at the block's end and come first in the DOM. A short
detail sits beside the controls and one too long for the space left takes a row of its own, so the header's height is
not fixed and the code moves when the rows needed differ between subjects. Each detail carries its own fade and
tooltip. The controls sit in fixed places in that group (the copy-path button, then the Markdown view choice, then the layout
choice, then the wrap choice), so the Tab order among them is the order on screen. The copy-path button is `useCopyPath`
(`src/components/`) over the platform's `clipboard`, and is absent without one. `LayoutToggle` is drawn by
whatever draws a diff and portalled into the layout slot of the `ControlsSlot` context (`controlsSlot.ts`), so it is
there while a choosable diff is (a diff's toggle goes with its renderer when that fails). The wrap choice is drawn once by the header (`WrapToggleHost`) for as
long as anything that draws code holds a claim on it with a mounted `WrapToggle`, so any number of code views, or an
image change whose sides both fell back to text, share one button. The layout toggle and its
persisted preference `diffLayout` are in `diffLayout.tsx`, the wrap toggle and `wordWrap`, one choice for files and
diffs, unwrapped until chosen, in `wordWrap.tsx` (keys in `preferenceKeys.ts`); the status
letters and colours are `STATUS_MARKS` and the word naming each status on its own `STATUS_LABELS` (both in
`statusMarks.ts`); the letter is drawn as `StatusChip` by the viewer's title, beside the word, and by the Git mode's
change list alike, where a change row's letter says the word in a tooltip. Untracked has a colour of its own (`--untracked` and `--untracked-foreground` in `style.css`, applied
as `.chip-untracked`), as no HeroUI colour fits it. A staged or unstaged change also carries a neutral stage tag after
the status chip (`ViewerSubject.stage`); conflicted, untracked and compared changes have none.

**Interface.** The application owns it and no rendering-library type crosses it, so the renderer can be replaced
without touching the daemon contract or the callers.

- `ViewerSubject` (`content.ts`): `key` (its identity, which the caller composes from project, source and path; a new
  key drops what was shown before), the wire `path`, an optional `source` wording (a `ReactNode`, so a name in it can be isolated from the text around it) and its plain-text `sourceText` for a tooltip, an optional `stage` tag (a staged or unstaged change's), an optional `status` (a `StatusKey` the caller gives, known before the read and kept if it fails; without it the chip comes from the change's sides) and a `ViewerContent`: `loading`,
  `error`, `file` (a `ViewerBody`: text, image or binary), `change` (a `ViewerChange`: an old and a new side, each
  `present`, `absent` or `out_of_scope`, mirroring the protocol's change sides, plus the change's unified patch, or the
  reason it could not be read, and, where both sides are files, `loadBodies`, which reads their whole text for
  expanding the lines the patch collapses; its `ChangeBodiesError` says why a read gave nothing) or `conflict` (a path in conflict: the caller's wording of how, above its file on disk).
- `bodyFromFileContent` turns the daemon's file reply into a `ViewerBody`; `changeStatus` and `changePresentation`
  are the pure rules that word a change and choose how it is shown (a diff, a side alone, one side restricted, images,
  binary, no differences, a rename with nothing else changed); every text change is one diff, a type change included,
  including one into or out of a path below itself, which git writes as a removal section plus an addition section and
  `joinedPatch` (`patch.ts`) joins into one patch; a diff `joinedPatch` rewrote holds both sides whole, so it is not
  expandable (the text presentation's `expandable`) and is given no `loadBodies`. A rename into or out of a path below
  itself that keeps its kind arrives as one ordinary section and is expandable like any other diff. A renamed change
  whose patch shows nothing changed (`saysNothingChanged`) is the `renamedUnchanged` presentation, not a diff.
- `src/viewer/patch.ts` is the viewer's patch-text work, importing nothing: `joinedPatch` (the two-section shape
  joined into one hunk, any other shape left as it is), `withoutNoNewlineMarkers` (git's "no newline" lines taken out
  of a drawn patch, to be said in a notice), `hasHunks`, `saysNothingChanged`, `hasTwoSides`, `hunkCounts` and `LINK_MODE` (a symbolic link's
  patch).
- `FileViewer({ subject, onClose, navigation?, location? })` (`FileViewer.tsx`): stays mounted while its subject changes, with
  `subject.key` as the dialog's reset key; `navigation` gives Previous / Next callbacks, a missing one disabling its
  button. `location` is the document's `MarkdownLocation` apart from its path (see **Markdown**). It reads the theme from `useOctoboardTheme`, so it must sit under `ThemeProvider`. Left and Right do what Previous
  and Next do, mirrored under right-to-left, handled on the dialog so the key never reaches the terminal; `arrowKeys.ts`'s
  `arrowNavigation` decides when they do not (a modifier, an input method composing, a control that uses the arrows
  itself, selected text).
- `Dialog` (`src/dialogs/`) also owns the scrolling of every dialog's body: the children sit in a `FadedScroller`, so an overflowing body fades at the edge it can still be scrolled towards and a dialog never builds a scroll container of its own. It gained `size="viewer"` (the window less a margin, up to 1440px wide), `footer={null}` and
  an element `title` for it. Every dialog, and the project pane (`ProjectBrowser`, and `LazyProjectBrowser`'s
  load-failure state, through `AsidePane`'s `className`), also takes the `control-fills` class (`style.css`), which
  gives HeroUI's `--default` colour family fills of its own (`--control-fill`, `--control-fill-hover`) so a neutral
  tag, the footer and close buttons and the view choices read against the surface; the rule's comment lists what it
  reaches. `ReportPanel` sits on the same surface as the pane and does not take it.
- `src/wirePath.ts`: `displayWirePath` / `wireBaseName` decode the daemon's wire paths for display only; a request
  always sends the wire form back unchanged.

**Markdown.** A Markdown file (`isMarkdownName` in `content.ts`) is shown by `MarkdownSurface.tsx` as a rendered document or as its source, chosen by a toggle in the header's Markdown view slot (`MarkdownViewToggle`, the persisted preference `markdownView`, in `markdownView.tsx`; the document until chosen). A file past the highlighting budget has no document and no toggle: it is the plain text it already falls back to. The document itself is `MarkdownDocument.tsx`, the one module importing `react-markdown`, `remark-gfm` and `remark-math`, loaded lazily into a build chunk of its own. Raw HTML in the text stays text. A mermaid fence is drawn by `MermaidBlock.tsx` through `renderDiagram` in `diagramConfig.ts`, a formula by `FormulaView.tsx` (KaTeX), and a project image by `DocumentImage.tsx`, which reads the file through the daemon without the viewer's read slot and shows a `data:` URL; those libraries load on first use. `projectAddress.ts` resolves a link or image address against the document path (`resolveProjectAddress`): an in-document anchor, an external http, https or mailto address, a project file, or refused. `openableAddress` lives there and is re-exported from `MarkdownDocument.tsx`. The document does not navigate the window: an anchor is revealed in place (`revealInDocument`), a project file is handed to `onOpenFile`, and an external address to the platform's `links` capability. `markdownLocation.tsx` holds the `MarkdownLocation` context (`path`, `project`, `anchor`, `onOpenFile`, `isDirectory`); `FileViewer`'s prop for it is `location`. The project browser (`src/browser/ProjectBrowser.tsx`) passes that prop (`openLinkedFile`); `listingSaysDirectory` in `src/browser/tree.ts` answers `isDirectory`, and `dismissViewer` in `src/browser/useGitReview.ts` is how a linked file leaves the change viewer. `markdownPlugins.ts` holds the remark and rehype plugins: `prepareMarkdown` adjusts inline dollar math to what GitHub draws and applies the diagram, formula and image budgets (the caps `documentDiagrams`, `documentDiagramChars`, `documentFormulas`, `documentFormulaChars`, `documentImages` and `documentImageBytes` in `budgets.ts`), `limitFences` decides which fences stay highlighted, and `headingIds` gives heading ids via `github-slugger`. A notice inside a paragraph is `InlineNotice` in `inlineNotice.tsx`. Each block's text direction is set explicitly rather than left to `dir="auto"`: `blockDirection.ts` holds `firstStrongDirection`, the direction of the first strong character in a syntax-tree node's text, descendants included, which `MarkdownDocument.tsx` gives each heading, paragraph, list, quote and table, and the document's own frame, falling back to the application's direction. A fenced block is drawn by `FencedCode.tsx` through the same Shiki renderer as the source view, within the `documentFences` and `documentFenceChars` budgets, and is plain text past them. The document's frame handles Select All and copy itself (`selectDocument` and `copyDocument` in `selectAll.ts`), so a whole-document copy puts the Markdown source on the clipboard.

**Files.** `codeTheme.ts` holds `CODE_THEMES`, the shared viewer reading-surface colours and syntax theme names; `patch.ts` the patch-text work above; `FrameSurface.tsx` holds `FrameSurface`, the tertiary HeroUI surface that frames every viewer area (plain text, code, diff, the rendered Markdown document, an image's checkerboard) and, through its `focused` prop, draws the focus ring of the reading surface it holds, which that surface's own fade would clip; `CodeSurface.tsx` holds `PlainText`, the code frame, `CodeSurface` and `DiffSurface`; `codeRenderer.tsx` lazy-loads `renderer.tsx`, the only module that
imports `@pierre/diffs`, and holds the lazy `HighlightedFile` / `RenderedDiff`, the `RendererBoundary` error boundary and `useRendererScope` (the worker pool's lifetime); `viewerStates.tsx` the `Notice`, `Loading`, `LoadingOverlay` and `Unreadable` lines; `slotToggle.tsx` the header icon toggle that `LayoutToggle` (`diffLayout.tsx`) and `MarkdownViewToggle` are built on; `MarkdownSurface.tsx`, `MarkdownDocument.tsx`, `projectAddress.ts`, `markdownPlugins.ts`, `markdownLocation.tsx`, `diagramConfig.ts`, `MermaidBlock.tsx`, `FormulaView.tsx`, `DocumentImage.tsx`, `inlineNotice.tsx`, `FencedCode.tsx`, `blockDirection.ts` and `markdownView.tsx` the Markdown view above; `budgets.ts` the renderer budgets; `expansion.ts` the expansion of a diff's collapsed lines (see "Renderer"); `rendererDom.ts` the library's markup it and the code selection read and set; `format.ts` file-size wording; `arrowKeys.ts` the arrow-key rule above (an input method's keys it leaves alone by `isImeKey`, from `src/imeKey.ts`); `themeShim.ts` the theme
shim below.

**Renderer.** `@pierre/diffs` 1.5.2 over Shiki 4.5.0, with the library's default JavaScript regex engine, so nothing
depends on WebAssembly (the CSP does not block it, but the viewer does not use it). It tokenizes in a pool of two
workers kept for as long as any viewer is open. `@pierre/diffs`, `@pierre/theming`, `@shikijs/themes` and `shiki` are
exact-pinned in `package.json`, since the theme shim below reaches into the first two's internals and the viewer's own code
depends on `@pierre/diffs`'s markup and instance, which no type signature guards; an upgrade of it is re-checked against five
things. (1) The markup `rendererDom.ts`, the one module that reads and sets it, names: the separator markup (`data-separator` with
`data-expand-index`, the `data-expand-*` buttons, the label attributes, `data-whole-file`) and the `[data-content]` columns
for the code range. (2) What `renderer.tsx` and `expansion.ts` rely on beyond the markup: the instance `onPostRender` hands over,
of which only `expandHunk` is used, with its gap numbering and `up` / `down` / `both` directions; `expansion.ts`'s own
listeners on the shadow root running before the library's; and the library redrawing the separators after each expansion.
(3) The `[data-code]` the drawn check in `renderer.tsx` looks for. (4) The `diffCss` sheet in `renderer.tsx`, whose selectors
(`data-line`, `data-line-type`, `data-diff-span`, `data-separator`, `data-expand-button`) and `--diffs-fg-number` custom property
name the library's own markup and styling; `readingCss` sets its shadow-root `--diffs-bg` to the shared reading surface. (5) The theme shim below. Shiki's themes are
`github-light-high-contrast` / `github-dark-high-contrast`, the only bundled pair whose every token meets 4.5:1.
`react-diff-view` is the recorded fallback should `@pierre/diffs` regress. A change is drawn from its patch: the
library's two-body line diff runs on the main thread and cannot be stopped, so the viewer never compares bodies, and a
text change without a patch says there is no diff to show. The runs of unchanged lines a patch collapses stay
collapsed until asked for: the separators are the only interactive part of the rendered code, and `expansion.ts`
drives them (their wording in the app's language, a step of lines per expansion growing to the rest of the gap, and
keyboard access). The first expansion of a diff calls the change's `loadBodies`, which hydrates the change from the
daemon's `…_change_bodies` requests (through `useChangeReader`, naming the versions the patch reply reported), and the
text it returns is handed to the library only to reveal lines, never to compare. A change whose bodies cannot be had, or
are past the budget, keeps its separators as they are; one that has moved on since its patch was read says so. Long
lines wrap only when the user chose it (`wordWrap`, handed to the library as its `overflow` option). Unwrapped, the
library scrolls them sideways in its own elements inside its shadow root, which cannot take keyboard focus and are not
the viewer's focusable frame, so a keyboard user reaches a long line by wrapping; wrapped, the one scroller is the
frame.

**Images.** PNG, JPEG, GIF, WebP, BMP, ICO and SVG are guaranteed; AVIF shows only where the system's WebKit decodes
it (macOS 13 and later). They render through `<img>` from `data:` URLs, which is what the window's `img-src data:`
admits, so an SVG's scripts never run and its external references are never fetched. An image counts as undecodable
by its `error` event, not by its size or `img.decode()`; an SVG that cannot be decoded is shown as its text. An image
change shows Before and After panes side by side, with no pixel diff. A restricted (`out_of_scope`) side is shown
alone, as a file, under a warning naming the other side's repository path; it is never drawn as a diff or as an
empty side, which only an `absent` side is.

**Budgets and fallbacks** (`budgets.ts`, separate from the daemon's read budgets). A file past 10,000 lines or
1,000,000 UTF-16 units is shown as plain preformatted text; a line past 1,000 characters is left untokenized inside
highlighted code; a patch past 10,000 lines or 1,000,000 UTF-16 units is shown as the plain patch; bodies past the same limits are not
used to expand (`bodiesPlan`). A grammar or theme
that fails to load, or an unknown language, shows plain text with a notice; a patch the library cannot read, a
renderer that throws or a renderer chunk that fails to load is caught by an error boundary and shows the raw patch
(or plain text) with a notice; a non-image binary shows "cannot be displayed" with its size.

**Theme shim.** The library reaches every bundled theme through `@pierre/theming/themes` and Shiki's internal
`themes.mjs`, which would put about 1.8 MB of theme chunks in a build. The `octoboard-viewer-themes` plugin in
`vite.config.ts` redirects both to `src/viewer/themeShim.ts`, which offers only the two themes in use under both
modules' exports, and fails the build if either real module still enters it, as a dependency update renaming one
would otherwise bring every theme back unnoticed. The dev server's pre-bundled dependencies and the tests keep every
theme. The app imports the viewer through the lazily loaded project browser, so a build carries about 250 lazy grammar
chunks (`dist/` is about 12 MB in about 253 assets) plus the renderer chunk, the worker and the browser's own chunk
(about 82 kB), which load on first use; the main chunk is about 1,280 kB.

**What was verified where.** The window's policy allows this UI's own font files (`font-src 'self'` in `index.html`). In the packaged WebView (origin `tauri://localhost`), grammar and
theme chunks load as `script-src 'self'` module chunks, the worker loads as a `self` module worker and answers, images
load from `data:`, and the library's injected styles in its shadow roots apply under `style-src 'unsafe-inline'`; every
gallery subject rendered as described above, focus stayed inside the dialog across subject changes, light and dark
rendered, and no content ran. In a plain WebKit browser over the gallery, with real pointer and keyboard input:
selecting and copying code (line numbers and diff markers are not copied), the Tab order, closing with focus restored
to the opener, narrow widths and right-to-left controls (code and paths keep their own direction); Chromium rendered
the same subjects. Real-input copying, the Tab order, narrow widths and right-to-left were not exercised in the
packaged window.
