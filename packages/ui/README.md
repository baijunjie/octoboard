# Octoboard UI

`@octoboard/ui`: a HeroUI 3 + React 19 + Tailwind 4 + Vite application, the UI of the desktop application. The macOS
shell in [`../../apps/desktop/`](../../apps/desktop/README.md) loads this package's `dist/` (bundled into the
application, not served by the daemon), and the same build also runs in a plain browser. It has the window chrome (a
top bar across the window and a left rail), the content panel under it holding the sidebar, the terminal pane and the
aside (a console session's report panel or a project's browser, its files, its worktrees' uncommitted changes and a comparison of two local branches), the archive view, the dialogs and the settings dialog, toasts and the failure screens,
all in the user's language (see `src/i18n/` below).

It talks to `octoboardd` (see [`../../apps/daemon/`](../../apps/daemon/README.md)) only over the WebSocket protocol in
[`../../apps/daemon/PROTOCOL.md`](../../apps/daemon/PROTOCOL.md), and reaches anything native (quit flow, system
notifications, Dock badge, the native window's own theme, the window chrome, the app menu, the menu bar icon) only through the platform
adapter, which is chosen once at startup.

## Development

This is a package of the repository's pnpm workspace: install from the workspace root with `pnpm install`, then run
the scripts from this directory.

- `pnpm dev` — the Vite dev server on port 5174, which is also what `pnpm tauri dev` in `apps/desktop/` starts and
  opens its window on.
- `pnpm gallery` — the same dev server on port 5175, opening the UI state gallery (below) in the browser.
- `pnpm typecheck` — `tsc --noEmit`.
- `pnpm test` — `vitest run`: the unit tests beside the code (`*.test.ts`), for the pure modules, plus jsdom tests for stateful classes and components (`*.test.ts`, `*.test.tsx`).
- `pnpm build` — typechecks, runs the catalog check (`vitest run src/i18n`), then writes `dist/` with relative asset
  paths, so a static server or a shell can serve it from any path. Opening `dist/index.html` over `file://` does not
  work: Chrome refuses module scripts from a `null` origin.

### The UI state gallery

The dev server serves a dev-only gallery of states that are hard to reach against a live daemon at `/gallery.html` (no
daemon needed): `pnpm gallery` serves it on port 5175 and opens it, and under `pnpm dev` it is at
`http://localhost:5174/gallery.html`. Pick a scenario from the list; light/dark, any offered language (`ar` is the
right-to-left one) and the window width are controls above the window, and all of them are in the URL, so a link
reproduces a view. The window is an iframe, so its width decides the `docked` breakpoint (1148px) for real. The real
`App` renders over a fixture daemon (`src/gallery/fixtureDaemon.ts`). A scenario's page writes its `octoboard.*` and
`heroui-theme` entries into `localStorage` on every load; on port 5174 that origin is the dev app's own, so opening the
gallery there resets the dev app's preferences, which `pnpm gallery`'s port avoids. A scenario's page sets
`data-gallery-ready` on `<html>` once its steps have run, which is what automation waits on before capturing. A
frame URL with `chrome=1` gives the page the desktop window's `windowChrome` capability (`src/gallery/frame.tsx`), so
what only the desktop app offers, such as the window shortcuts, can be driven in a browser. Neither
gallery page is part of the bundle `pnpm build` writes, but `src/gallery/` is still type-checked by it, so a broken
fixture fails the build.

To add a scenario, add an entry to the file for its area in `src/gallery/fixtures/` (or a new file, listed in
`index.ts`); its `group` is one of the titles in `GROUPS` (`groups.ts`), where a new group gets the icon its heading
carries. Its `state` is built with `snapshotState` from the helpers in `builders.ts`, so a protocol change breaks it at
typecheck. State that lives in a component rather than the store (a dialog, the archive view, which session is selected)
is reached with `steps`, which press controls by name as a user would (`ui.press(ui.t("rail.settings"))`). `preferences`
sets what the app persists (pane visibility and widths, the sidebar's console and focus target), `toasts` raises daemon
errors and notices, and `terminal: "refuse"` makes a session's terminal unreachable.

### Pointing it at a daemon

The daemon binds an OS-assigned port. Start `octoboardd` and read the port from the first line it prints on stdout, or
from `$TMPDIR/octoboardd.port`. Then either:

- open `http://localhost:5174/?port=<port>`, or set `VITE_DAEMON_PORT`; or
- run `OCTOBOARD_DAEMON_PORT=<port> pnpm dev` and open the plain URL, which reaches the daemon through a same-origin
  `/ws` proxy (`vite.config.ts`).

Both variables can also be set in the committed repo-root `.env` (commented out there) or a gitignored `.env.local`;
a variable in the shell wins over them. The dev server reads those files and a `vite build` never does. Prefer them to
a `packages/ui/.env`: that directory is vite's own `envDir`, so a `vite build` reads it too and a `VITE_DAEMON_PORT`
there goes into a release bundle, and vite expands `$VAR` in it where the root files are read literally.

With none of these the page shows a "no daemon address" screen. A daemon started by hand for development should get an
isolated `HOME` and `TMPDIR`: its instance lock (`daemon.lock`) and database live under `$HOME/.octoboard`, and the
port file under the temp directory, so the defaults would touch the real data and collide with a running instance.

## The file viewer

`src/viewer/` is a read-only modal that shows one subject: a file's text or image, a change between two versions, or
the loading or failed state of either. It is for the project file browser and its change views; no edit or save
interaction exists, and repository content is only ever displayed as data, never inserted as markup. The app reaches it
only through the project browser (`src/browser/`), which is loaded lazily; the gallery's "File viewer" group exercises it
on its own (see "The UI state gallery").

The header is the title with the status chip, then a details block: the path, the comparison or source, the size and a
rename's origin are separate items (`DetailItem` in `FileViewer.tsx`, the path and the origin drawn as `PlainMarkedPath`
with a file icon) that flow around the view controls, which float at the block's end and come first in the DOM. A short
detail sits beside the controls and one too long for the space left takes a row of its own, so the header's height is
not fixed and the code moves when the rows needed differ between subjects. Each detail carries its own fade and
tooltip. The controls sit in fixed places in that group (the Markdown view choice, then the layout choice, then the
wrap choice), so the Tab order among them is the order on screen. `LayoutToggle` is drawn by
whatever draws a diff and portalled into the layout slot of the `ControlsSlot` context (`controlsSlot.ts`), so it is
there while a choosable diff is (a single diff's toggle goes with its renderer when that fails; a change in sections
keeps it even if every section's renderer has). The wrap choice is drawn once by the header (`WrapToggleHost`) for as
long as anything that draws code holds a claim on it with a mounted `WrapToggle`, so any number of code views, a change
in sections or an image change whose sides both fell back to text, share one button. The layout toggle and its
persisted preference `diffLayout` are in `diffLayout.tsx`, the wrap toggle and `wordWrap`, one choice for files and
diffs, unwrapped until chosen, in `wordWrap.tsx` (keys in `preferenceKeys.ts`); the status
letters and colours are `STATUS_MARKS` (`statusMarks.ts`), drawn as `StatusChip` by the viewer's title and the Git mode's
change list alike. Untracked has a colour of its own (`--untracked` and `--untracked-foreground` in `style.css`, applied
as `.chip-untracked`), as no HeroUI colour fits it. A staged or unstaged change also carries a neutral stage tag after
the status chip and before the name (`ViewerSubject.stage`); conflicted, untracked and compared changes have none.

**Interface.** The application owns it and no rendering-library type crosses it, so the renderer can be replaced
without touching the daemon contract or the callers.

- `ViewerSubject` (`content.ts`): `key` (its identity, which the caller composes from project, source and path; a new
  key drops what was shown before), the wire `path`, an optional `source` wording (a `ReactNode`, so a name in it can be isolated from the text around it) and its plain-text `sourceText` for a tooltip, an optional `stage` tag (a staged or unstaged change's), an optional `status` (a `StatusKey` the caller gives, known before the read and kept if it fails; without it the chip comes from the change's sides) and a `ViewerContent`: `loading`,
  `error`, `file` (a `ViewerBody`: text, image or binary), `change` (a `ViewerChange`: an old and a new side, each
  `present`, `absent` or `out_of_scope`, mirroring the protocol's change sides, plus the change's unified patch, or the
  reason it could not be read, and, where both sides are files, `loadBodies`, which reads their whole text for
  expanding the lines the patch collapses; its `ChangeBodiesError` says why a read gave nothing) or `conflict` (a path in conflict: the caller's wording of how, above its file on disk).
- `bodyFromFileContent` turns the daemon's file reply into a `ViewerBody`; `changeStatus` and `changePresentation`
  are the pure rules that word a change and choose how it is shown (a diff, the two sections of a type change, a side
  alone, one side restricted, images, binary, no differences), with `patchSections` splitting a patch into the
  sections drawn on their own and `withoutNoNewlineMarkers` taking git's "no newline" lines out of a drawn patch to be
  said in a notice.
- `FileViewer({ subject, onClose, navigation? })` (`FileViewer.tsx`): stays mounted while its subject changes, with
  `subject.key` as the dialog's reset key; `navigation` gives Previous / Next callbacks, a missing one disabling its
  button. It reads the theme from `useOctoboardTheme`, so it must sit under `ThemeProvider`. Left and Right do what Previous
  and Next do, mirrored under right-to-left, handled on the dialog so the key never reaches the terminal; `arrowKeys.ts`'s
  `arrowNavigation` decides when they do not (a modifier, an input method composing, a control that uses the arrows
  itself, selected text).
- `Dialog` (`src/dialogs/`) gained `size="viewer"` (the window less a margin, up to 1440px wide), `footer={null}` and
  an element `title` for it. A viewer dialog also takes the `dialog-fills` class (`style.css`), which gives HeroUI's
  `--default` colour family the dialog's own fills (`--dialog-fill`, `--dialog-fill-hover`) so a neutral tag, the
  footer and close buttons and the view choices read against its surface; the rule's comment lists what it reaches.
- `src/wirePath.ts`: `displayWirePath` / `wireBaseName` decode the daemon's wire paths for display only; a request
  always sends the wire form back unchanged.

**Markdown.** A Markdown file (`isMarkdownName` in `content.ts`) is shown by `MarkdownSurface.tsx` as a rendered document or as its source, chosen by a toggle in the header's Markdown view slot (`MarkdownViewToggle`, the persisted preference `markdownView`, in `markdownView.tsx`; the document until chosen). A file past the highlighting budget has no document and no toggle: it is the plain text it already falls back to. The document itself is `MarkdownDocument.tsx`, the one module importing `react-markdown` and `remark-gfm`, loaded lazily into a build chunk of its own; it is inert (raw HTML in the text is shown as text, an image as its alt text, and a link's address is only handed to the platform's `links` capability, never followed by the window). A fenced block is drawn by `FencedCode.tsx` through the same Shiki renderer as the source view, within the `documentFences` and `documentFenceChars` budgets, and is plain text past them. The document's frame handles Select All and copy itself (`selectDocument` and `copyDocument` in `selectAll.ts`), so a whole-document copy puts the Markdown source on the clipboard.

**Files.** `CodeSurface.tsx` holds `PlainText`, the code frame, `CodeSurface` and `DiffSurface`; `codeRenderer.tsx` lazy-loads `renderer.tsx`, the only module that
imports `@pierre/diffs`, and holds the lazy `HighlightedFile` / `RenderedDiff`, the `RendererBoundary` error boundary and `useRendererScope` (the worker pool's lifetime); `viewerStates.tsx` the `Notice`, `Loading`, `LoadingOverlay` and `Unreadable` lines; `slotToggle.tsx` the header toggle group that `LayoutToggle` (`diffLayout.tsx`) and `MarkdownViewToggle` are built on; `MarkdownSurface.tsx`, `MarkdownDocument.tsx`, `FencedCode.tsx` and `markdownView.tsx` the Markdown view above; `budgets.ts` the renderer budgets; `expansion.ts` the expansion of a diff's collapsed lines (see "Renderer"); `rendererDom.ts` the library's markup it and the code selection read and set; `format.ts` file-size wording; `arrowKeys.ts` the arrow-key rule above (an input method's keys it leaves alone by `isImeKey`, from `src/imeKey.ts`); `themeShim.ts` the theme
shim below.

**Renderer.** `@pierre/diffs` 1.5.2 over Shiki 4.5.0, with the library's default JavaScript regex engine, so nothing
depends on WebAssembly (the CSP does not block it, but the viewer does not use it). It tokenizes in a pool of two
workers kept for as long as any viewer is open. `@pierre/diffs`, `@pierre/theming`, `@shikijs/themes` and `shiki` are
exact-pinned in `package.json`, since the theme shim below reaches into the first two's internals and the viewer's own code
depends on `@pierre/diffs`'s markup and instance, which no type signature guards; an upgrade of it is re-checked against five
things. (1) The markup `rendererDom.ts`, the one module that reads and sets it, names: the separator markup (`data-separator` with
`data-expand-index`, the `data-expand-*` buttons, the label attributes, `data-whole-file`) and the `[data-content]` columns
for the code range. (2) What `renderer.tsx` and `expansion.ts` rely on beyond the markup: the instance `onPostRender` hands over,
of which only `expandHunk` is used, with its gap numbering and `up` / `down` / `both` directions; `expansion.ts`'s own
listeners on the shadow root running before the library's; and the library redrawing the separators after each expansion.
(3) The `[data-code]` the drawn check in `renderer.tsx` looks for. (4) The `diffCss` sheet in `renderer.tsx`, whose selectors
(`data-line`, `data-line-type`, `data-diff-span`, `data-separator`, `data-expand-button`) and `--diffs-fg-number` custom property
name the library's own markup and styling. (5) The theme shim below. Shiki's themes are
`github-light-high-contrast` / `github-dark-high-contrast`, the only bundled pair whose every token meets 4.5:1.
`react-diff-view` is the recorded fallback should `@pierre/diffs` regress. A change is drawn from its patch: the
library's two-body line diff runs on the main thread and cannot be stopped, so the viewer never compares bodies, and a
text change without a patch says there is no diff to show. The runs of unchanged lines a patch collapses stay
collapsed until asked for: the separators are the only interactive part of the rendered code, and `expansion.ts`
drives them (their wording in the app's language, a step of lines per expansion growing to the rest of the gap, and
keyboard access). The first expansion of a diff calls the change's `loadBodies`, which hydrates the change from the
daemon's `…_change_bodies` requests (through `useChangeReader`, naming the versions the patch reply reported), and the
text it returns is handed to the library only to reveal lines, never to compare. A change whose bodies cannot be had, or
are past the budget, keeps its separators as they are; one that has moved on since its patch was read says so. Long
lines wrap only when the user chose it (`wordWrap`, handed to the library as its `overflow` option). Unwrapped, the
library scrolls them sideways in its own elements inside its shadow root, which cannot take keyboard focus and are not
the viewer's focusable frame, so a keyboard user reaches a long line by wrapping; wrapped, the one scroller is the
frame.

**Images.** PNG, JPEG, GIF, WebP, BMP, ICO and SVG are guaranteed; AVIF shows only where the system's WebKit decodes
it (macOS 13 and later). They render through `<img>` from `data:` URLs, which is what the window's `img-src data:`
admits, so an SVG's scripts never run and its external references are never fetched. An image counts as undecodable
by its `error` event, not by its size or `img.decode()`; an SVG that cannot be decoded is shown as its text. An image
change shows Before and After panes side by side, with no pixel diff. A restricted (`out_of_scope`) side is shown
alone, as a file, under a warning naming the other side's repository path; it is never drawn as a diff or as an
empty side, which only an `absent` side is.

**Budgets and fallbacks** (`budgets.ts`, separate from the daemon's read budgets). A file past 10,000 lines or
1,000,000 UTF-16 units is shown as plain preformatted text; a line past 1,000 characters is left untokenized inside
highlighted code; a patch past 10,000 lines or 1,000,000 UTF-16 units is shown as the plain patch; bodies past the same limits are not
used to expand (`bodiesPlan`). A grammar or theme
that fails to load, or an unknown language, shows plain text with a notice; a patch the library cannot read, a
renderer that throws or a renderer chunk that fails to load is caught by an error boundary and shows the raw patch
(or plain text) with a notice; a non-image binary shows "cannot be displayed" with its size.

**Theme shim.** The library reaches every bundled theme through `@pierre/theming/themes` and Shiki's internal
`themes.mjs`, which would put about 1.8 MB of theme chunks in a build. The `octoboard-viewer-themes` plugin in
`vite.config.ts` redirects both to `src/viewer/themeShim.ts`, which offers only the two themes in use under both
modules' exports, and fails the build if either real module still enters it, as a dependency update renaming one
would otherwise bring every theme back unnoticed. The dev server's pre-bundled dependencies and the tests keep every
theme. The app imports the viewer through the lazily loaded project browser, so a build carries about 250 lazy grammar
chunks (`dist/` is about 12 MB in about 253 assets) plus the renderer chunk, the worker and the browser's own chunk
(about 82 kB), which load on first use; the main chunk is about 1,280 kB.

**What was verified where.** The CSP is unchanged. In the packaged WebView (origin `tauri://localhost`), grammar and
theme chunks load as `script-src 'self'` module chunks, the worker loads as a `self` module worker and answers, images
load from `data:`, and the library's injected styles in its shadow roots apply under `style-src 'unsafe-inline'`; every
gallery subject rendered as described above, focus stayed inside the dialog across subject changes, light and dark
rendered, and no content ran. In a plain WebKit browser over the gallery, with real pointer and keyboard input:
selecting and copying code (line numbers and diff markers are not copied), the Tab order, closing with focus restored
to the opener, narrow widths and right-to-left controls (code and paths keep their own direction); Chromium rendered
the same subjects. Real-input copying, the Tab order, narrow widths and right-to-left were not exercised in the
packaged window.
