# Desktop shell structure (`apps/desktop/`)

`@octoboard/desktop`: the Tauri 2 shell of the macOS and Windows desktop applications. Its Rust crate `octoboard`
(`apps/desktop/src-tauri/`, library `app_lib`, Tauri `~2.12` with the tray-icon and macOS private-API features, plus the
shell, notification, clipboard, dialog and updater plugins, and off macOS the single-instance plugin) is a member of the root Cargo workspace beside
`apps/daemon/`. The npm package holds only the build, install, release and release-publishing scripts. The shell has no
UI of its own: the window loads the UI of `packages/ui/`, bundled at build time, and starts `octoboardd` as a sidecar.

The shell never carries daemon traffic. The UI talks to the daemon over the WebSocket/HTTP protocol
([`PROTOCOL.md`](../../apps/daemon/PROTOCOL.md)); the shell bakes the daemon's port and per-launch key and the system's
preferred languages, the host's facts (`host_facts.rs`) and the settings it holds itself (`app_settings.rs`) into the window's URL, restarts a daemon that ends unexpectedly and points the window at it, and
passes only bare signals, display values, opaque ids, macOS privacy grants, update information, the text of a file
the user saves or opens through the system dialog, the path of a directory the user chooses there, and the parts of a remote
daemon's file that a remote window copies to this computer over IPC.

Paths in this doc that do not start with `apps/` or `packages/` are relative to `apps/desktop/`.

## Directory map

### `src-tauri/`

A concern that differs by platform is a module with the shared surface in its `mod.rs` (or its own file) and the
implementations in `macos.rs` and `windows.rs` (a small concern keeps them as inline `mod macos` and `mod windows` in
its own file, as `languages.rs`, `notification_settings.rs`, `diagnostics.rs`, `open_address.rs`,
`remote/credentials.rs`, `remote/device_key.rs` and `sidecar/stop.rs` do); the rule for platform code is in
`docs/conventions/desktop-shell.md`, "Code that differs by platform".

| `src/daemon_window.rs`, `src/window_factory.rs` | One window per daemon: `daemon_window.rs` keeps which remote window (`daemon-<n>`) shows which daemon (by identity) and which window was focused last; `window_factory.rs` builds the windows (the main one and a remote daemon's, each on `index.html` with its `window_query`, hidden where its frame was last left; it counts each load of the main window's page for `remote/page.rs`), lets go of what a window lost before it showed its daemon leaves (`window_lost`), and arms the reveal safety net (`background::safety_net_shows`) |
| `src/badge.rs`, `src/notifications/` | What every daemon's window shares of the application: the Dock badge, the sum of the waiting sessions each window reports (`set_badge_count`), a window's share dropped as it closes; system notifications each window raises (`show_notification`), a click on one bringing that window forward, or the main one once it has closed. `notifications/plugin.rs` (every target but macOS): the notification plugin shows it, marked with the window's label, and reports the click to the handler `install` registers; `notifications/macos.rs`: the shell shows it itself through `mac-notification-sys` and waits on a thread per notification for the click, since the plugin reports none for a notification without buttons |
| `src/remote_login.rs` | Whether this computer's SSH server is on (macOS Remote Login, Windows OpenSSH Server) for the Remote access section of Settings (`remote_login_status`), and opening the system's settings where it is turned on (`open_remote_login_settings`) |

a counter of the main window's page loads lets a connection the page itself made, whose page was reloaded before it ended, hand its question or failure back (`should_hand_back`); only the main window may take either; `forward.rs` the loopback ports of a remote machine that a remote window opens in this computer's browser: only a loopback address is forwarded, to the remote machine's own loopback, over the window's SSH connection, and each forward is listed and stopped from the window (`remote_link_address`, `remote_forwards_list`, `remote_forward_stop`); `files/` the copies of a remote daemon's files kept on this computer for "Download and open" (`remote_file_begin`, `remote_file_write`, `remote_file_open`, `remote_file_discard`): it stores the parts the page reads from the daemon, refuses names that `config/launchable-extensions.json` lists, opens the copy through `open_address.rs` and removes every copy at the next start (`clear`). The platform modules apply private permissions and mark the copy as downloaded. |
| `src/app_settings.rs`, `src/config_dir.rs` | The two settings the shell must know before any page has loaded (run in the background, show the menu bar icon): `settings.json` in the app config directory, read once in `setup` before the tray is created, held in managed state, handed to the page as the window's `settings` query parameter (`current_json`; `recovery.rs` rebuilds it with the current values) and changed by the page through `set_app_settings`, which applies the change to `background.rs` and `tray/` and rewrites the file. `config_dir.rs` is the config directory's path and the atomic JSON write that `app_settings.rs` and `window_state.rs` share |
| `src/window_state.rs`, `src/page_isolation/`, `src/diagnostics.rs` | Remembering and validating the window frame (`initial_window` never fits it below `MIN_SIZE`, so on a screen smaller than that, such as 1024×768, Windows caps the width at the screen's, and the layout stays usable; what the system frame adds around the inner size is `chrome::SystemFrame`); blocking non-image `http(s)` requests in the window's webview, which on macOS is a WebKit content rule list (with a development-only localhost exception) and on Windows a WebView2 `WebResourceRequested` filter installed on the built window (`install`, answering 403; `policy.rs` decides, letting through images, the app's own `tauri.localhost` and `ipc.localhost`, and in debug builds `localhost`), and nothing on Linux; the `diagnostic!` log to stderr and `desktop.log` under `~/.octoboard/logs/`, where the home is `USERPROFILE` on Windows and `HOME` elsewhere, as the daemon reads it |
| `capabilities/default.json`, `capabilities/remote.json`, `capabilities/remote-window.json`, `capabilities/flyout.json`, `permissions/*.toml` | The IPC allowlists (the main window's; `remote.json` for the remote windows, which get none of the remote daemons' commands; `remote-window.json` for the remote windows alone, which add port forwarding and the file copies; the tray flyout's) and the app-defined permission files they name |
| `tauri.conf.json`, `tauri.macos.conf.json`, `tauri.windows.conf.json`, `windows/installer-hooks.nsh`, `Info.template.plist`, `Entitlements.plist`, `icons/`, `images/`, `licenses/` | Where the window's UI comes from (`index.html` with the window's query, which Tauri resolves against `devUrl` under `tauri dev` and against the bundled assets otherwise), the `octoboardd` `externalBin`, the public key that verifies the update archive (`createUpdaterArtifacts` is off: the scripts make and sign the archive); ### [`scripts/`](../../apps/desktop/scripts/README.md) (`apps/desktop/scripts/`)

The native-resource generation, sidecar build (`build-daemon.mjs`: the daemon with the UI build embedded, which it builds first when `packages/ui/dist` is missing), local build, local install, version preparation, release, update-signing
and release-publishing scripts, with their shared `bundle.mjs`, `update-archive.mjs` (packs and signs the update
archive), the testable `release-manifest.mjs` (which manifests each platform writes, the platform selection and the tag message's `Platforms:` line) and the temporary `actool/` shim. `release.mjs` dispatches on the host to
`release-macos.mjs`, `release-windows.mjs` or `release-linux.mjs` (which builds the daemon's Linux server archive, with the daemon's `self-update` feature on, which no other build turns on; the Linux release has no desktop shell in it); `windows-release.mjs` holds the Windows signing modes, the `signtool`
checks and the installer inspection, `linux-release.mjs` the Linux release's target, static-link check and archive checksum helpers, and `sign-file.mjs` is the per-file sign command of the `command` mode. `release-desktop.mjs` owns the
`release:version` command that prepares and pushes a version for CI (`--platforms` for a version of some platforms); `tag-message.mjs` reads a tag message for `.github/release-notes.sh`. `publish-release.mjs` publishes the selected platforms (`--platforms`, all three by default), after `update-signature.mjs` has checked every update signature against the updater's public key. The module README holds the scripts' interfaces,
the automated and manual release procedures, failure recovery, and the rule that the version lives in two places.

## IPC surface

Commands permitted through `capabilities/default.json` and `permissions/*.toml`: the exit flow
(`frontend_exit_heartbeat`, `begin_quit`, `confirm_quit`, `daemon_exit_detail`), `set_menu_labels`, `set_tray_menu`,
`set_app_settings`, `set_keep_awake_shown`, `launch_at_login_status`, `set_launch_at_login`,
`open_login_items_settings`, `reveal_main_window`, `bring_to_front`, `permissions_status`, `request_permission`,
`open_privacy_settings`, `open_notification_settings` (also the Windows notification settings), `save_configuration_file`, `open_configuration_file`,
`pick_directory`, `check_for_update`, `install_update`, `set_badge_count`, `show_notification`, `remote_login_status` and
`open_remote_login_settings`; the remote daemons' commands (`remote_daemons_list`,
`remote_daemon_save`, `remote_daemon_remove`, `remote_daemon_connect`, `remote_daemons_status`,
`remote_daemon_disconnect`, `main_window_show`), with the Remote devices page's hand-over (`remote_connect_pending_take`,
`remote_page_requested_take`), all given to the main window alone (`capabilities/default.json`); the remote windows alone are also given
Try again's `remote_connection_retry`, the forwarding (`remote_link_address`, `remote_forwards_list`, `remote_forward_stop`) and the file copies (`remote_file_begin`,
`remote_file_write`, `remote_file_open`, `remote_file_discard`) in `capabilities/remote-window.json`; and the flyout's own (`tray_flyout_*`, `capabilities/flyout.json`).
Events to the webview: `settings-requested`, `remote-daemons-changed`, `remote-connect-pending`, `remote-page-requested`,
`about-requested`, `tray-session-chosen`, `tray-updates-requested`, `tray-menu-opened`, `exit-requested` and
`daemon-exited`; to a remote window alone, `remote-forwards-changed` and `remote-connection-up` (its SSH connection
is up again).
`packages/ui/src/platform/tauri.ts` maps commands and events onto the platform adapter's capabilities; it is the UI's
only counterpart of this surface.

## Dependency direction

- The shell depends on the daemon only as a sidecar executable and a handshake line; the UI depends on the shell only
  through the platform adapter. Neither the Rust crate nor the scripts import daemon code.
- `src-tauri/build.rs` reads the repo-root `config/app.json`; the scripts use `scripts/lib/env.mjs` and `scripts/lib/git.mjs` at
  the repository root.

## Where new code goes

- A new native capability the UI needs: a module in `src-tauri/src/`, with its command, permission file and adapter
  capability as `docs/conventions/desktop-shell.md`, "What the shell carries" lists; the same section covers a
  difference by OS the UI must know of (a field of `host_facts.rs` and `HostFacts`) and what does not belong in the
  shell (a command that carries daemon data).
- Menu bar icon work stays inside `src/tray/`: parse in `model.rs`, build in `items.rs`, pictures in `icon.rs`, the
  words daemons are named by in `names.rs`, native-only finishing in `macos/` (`windows.rs` for its counterpart, the
  Windows flyout in `flyout.rs`, what it draws in `flyout_model.rs`, the tabs in `tabs.rs`).
- A daemon window's building goes in `window_factory.rs`, which window shows which daemon in `daemon_window.rs`, and remote
  daemon work in `src/remote/` by the split above.
- Code that differs by platform goes into the concern's `macos.rs` and `windows.rs` (or its inline `mod macos` and `mod
  windows`) behind the shared surface its `mod.rs` selects; what shared code may still carry is in
  `docs/conventions/desktop-shell.md`, "Code that differs by platform".
- A desktop build or release command belongs in this package's `scripts/` and `package.json`. Build steps share
  `bundle.mjs`. The part of publishing that needs no GitHub goes in `release-manifest.mjs`, which reads the holder
  floor from `config/holder-floor.txt` and can be tested locally.

## Shared entry points

The rows are the helper list; the prohibitions behind some of them are in `docs/conventions/desktop-shell.md`, "Shared
entry points with a rule behind them".

| Need | Entry point |
|---|---|
| A diagnostic line | the `diagnostic!` macro (`src/diagnostics.rs`) |
| Write a JSON file under the app config directory | `config_dir::write_json` (path from `config_dir::config_path`) |
| A setting the shell must know before the page loads | a field of `AppSettings` in `src/app_settings.rs`, applied in `set_app_settings`; the page side is `createShellPreference` (`packages/ui/src/lifecycle/shellSettings.ts`) |
| Stop the daemon before a restart or quit | `sidecar::stop_daemon` with a `StopKind`: waits for the daemon to exit after the UI's request, then sends `POST /shutdown` (`request_stop` in `sidecar/stop.rs`), or SIGTERM on macOS when the request fails (the platform half of `terminate` in `sidecar/stop.rs`; Windows has no signal), then kills (`TerminateProcess` on Windows); the update restart's `Planned` kind sends `POST /planned-stop` instead (repeated once, never SIGTERM) and waits 30 s (above the time the daemon takes to save the screens in the worst case) for the screens to be saved before it kills, and the user's session ending takes `stop_daemon_at_session_end`, with no wait for the UI and within one time budget (the request included), ending a planned stop that is under way instead of waiting for it. The sidecar is started through the shell plugin, which on Windows gives it a hidden console (`CREATE_NO_WINDOW`) |
| Relaunch, applying a downloaded update | `exit::confirm_quit` with `restart`: under the `installing` guard it shares with `quit_installing` and `install_on_exit`, it stops the daemon with the planned stop (`sidecar::stop_daemon`, `StopKind::Planned`; no quit note) and calls `updater::install_for_restart`, which on Windows starts the held installer with the relaunch, ending the process after saving `window_state`, remembering the open remote windows for the relaunch to bring back (`remote::remember_windows`, once per process) and removing the tray icon, and on macOS does nothing; when it returns, the guard is given back and `lifecycle::relaunch` ends the process and starts the application again |
| End the application, installing a downloaded update | `exit::on_exit_requested` and `exit::on_exit`, which stop the daemon (the ordinary stop) and call `updater::install_on_quit` (Windows; nothing is held on macOS) |
| Open a System Settings pane, a Settings page or the browser | `open_address::open` (macOS pane addresses in `system_settings.rs`) |
