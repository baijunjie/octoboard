# Desktop shell structure (`apps/desktop/`)

`@octoboard/desktop`: the Tauri 2 shell of the macOS and Windows desktop applications. Its Rust crate `octoboard`
(`apps/desktop/src-tauri/`, library `app_lib`, Tauri `~2.12` with the tray-icon and macOS private-API features, plus the
shell, notification, clipboard, dialog and updater plugins, and off macOS the single-instance plugin) is a member of the root Cargo workspace beside
`apps/daemon/`. The npm package holds only the build, install, release and release-publishing scripts. The shell has no
UI of its own: the window loads the UI of `packages/ui/`, bundled at build time, and starts `octoboardd` as a sidecar.

The shell never carries daemon traffic. The UI talks to the daemon over the WebSocket/HTTP protocol
([`PROTOCOL.md`](../../apps/daemon/PROTOCOL.md)); the shell bakes the daemon's port and per-launch key and the system's
preferred languages, the host's facts (`host_facts.rs`) and the settings it holds itself (`app_settings.rs`) into the window's URL, restarts a daemon that ends unexpectedly and points the window at it, and
passes only bare signals, display values, opaque ids, macOS privacy grants, update information, the text of a file
the user saves or opens through the system dialog, and the path of a directory the user chooses there over IPC.

Paths in this doc that do not start with `apps/` or `packages/` are relative to `apps/desktop/`.

## Directory map

### `src-tauri/`

A concern that differs by platform is a module with the shared surface in its `mod.rs` (or its own file) and the
implementations in `macos.rs` and `windows.rs` (a small concern keeps them as inline `mod macos` and `mod windows` in
its own file, as `languages.rs`, `notification_settings.rs`, `diagnostics.rs` and `sidecar/stop.rs` do); `windows.rs` serves every target but macOS, Linux included, where what needs a Windows API is compiled out or does nothing.

| Path | Role |
|---|---|
| `build.rs` | On macOS targets generates the native localization resources through `scripts/native-localizations.mjs`, exposes the app name and repository address from `config/app.json`; fails the build when `tauri.conf.json`, the workspace `repository`/`license` or the two version values disagree (the version lives in `apps/desktop/package.json` and the root `Cargo.toml`) |
| `src/host_facts.rs` | The facts the UI takes from the machine instead of inferring them (system, shortcut modifier, window chrome, which native features exist, the system's words), per target OS, serialised as the `host` query parameter; mirrors `HostFacts` in `packages/ui/src/platform/host.ts` |
| `src/lib.rs`, `src/main.rs` | `run()` builds the Tauri app, wires the menu, exit flow, close request and the platform's lifecycle hooks, and opens the hidden main window once page isolation is ready, dressed by the window chrome; `main.rs` is the binary entry: it first lets `app_lib::answer_permission_probe()` answer a `--screen-recording-probe` start (the process prints its Screen Recording grant and exits before the app starts), otherwise calls `run()` (a release build on Windows is a GUI subsystem program, so it opens no console window) |
| `src/chrome/`, `src/languages.rs` | The main window's frame (macOS: the overlay titlebar with the traffic lights and the translucent sidebar material; elsewhere the system's own frame) and, in `install`, what the built window's webview needs set on it (Windows: WebView2's browser accelerator keys, off in release builds and kept in debug builds, where reload and find help debugging); the system's preferred languages for the window's query (macOS; elsewhere none) |
| `src/sidecar/`, `src/recovery.rs` | `sidecar/mod.rs`: starting `octoboardd`, parsing its handshake line into the daemon's address, keeping `DaemonState` and a tail of its stderr; `sidecar/stop.rs`: stopping it, with the two kinds of stop (`StopKind`: the ordinary one that interrupts the sessions, the planned one of an update restart that hands them over), the stop at the end of the user's session (`stop_daemon_at_session_end`, within one time budget), and, at a session end during an update restart's planned stop, ending that stop (the signal and the shutdown request) instead of waiting for it; `sidecar/quit_note.rs`: the quit record `application-quit` in `~/.octoboard/`, left for every quit when the application had a daemon that may hold holders (`DaemonState.may_hold_holders`) and read by the next daemon start, and the quit note (`note_quit`, `note_session_end`, written once to the running daemon, or to one spawned around the quit, under the lock the child is stored under); `recovery.rs`: restarting a daemon that ended, with a budget and backoff, and telling the window when the budget is spent or when an update has replaced the application's files and waits for its restart (macOS; the daemon is then left alone, while a Windows update that is only downloaded still lets the daemon be restarted) |
| `src/exit.rs`, `src/background.rs`, `src/lifecycle/` | The exit-confirmation flow, and the way out that installs a downloaded update whichever way the quit got through (`on_exit_requested`, `install_on_exit`); the quit record and note every way out that is a quit writes for the daemon (`sidecar::note_quit`, via `begin_quit`, `quit_let_through` and `on_exit`) and the end of the user's session passed on to it once (`end_session`), which takes priority over the installer and the relaunch (`ExitState::commit_final_action`); running in the background behind the menu bar icon (the setting reaches it through `app_settings.rs`), `bring_to_front`, and revealing the window the shell created hidden (`reveal_main_window`; after a launch at login that keeps the app in the background it stays hidden, `start_in_background`); the platform's part around both (macOS: the `applicationShouldTerminate:` override, which tells a quit the system makes for a logout, restart or shutdown from a user's by the reason its Apple event carries and stops the daemon for the former without asking, the reopen and activation, leaving fullscreen and the Dock hide and show; Windows: `install` puts the application ahead of the daemon in the system's shutdown order so `end_session` can stop it before Windows ends its hidden console; off macOS, the single-instance plugin, registered first, whose callback shows the running window again when the app is launched a second time) |
| `src/launch_at_login/`, `src/apple_event.rs` | Launch at login: `launch_at_login_status`, `set_launch_at_login` and `open_login_items_settings` read and change the system's own entry (macOS: `SMAppService.mainApp`, macOS 13 and later, with a state that waits for the user's approval; Windows: the per-user Run registry value with `--launched-at-login`, honouring the Startup apps switch; `host_facts.rs` says whether the entry exists), nothing is remembered by the shell; a launch the system made for the entry is recognised once (`take_login_launch`, `login_launch_pending`). `apple_event.rs` (macOS) reads the enum code of an attribute or parameter of the Apple event being handled, shared by the quit-reason check in `lifecycle/macos.rs` and the login-launch check |
| `src/menu/`, `src/tray/` | The native menu bar built from the UI's labels (`macos.rs`; elsewhere no menu is set and `set_menu_labels` accepts the labels and does nothing); the menu bar icon: `mod.rs` creation and `set_tray_menu`, `model.rs` the menu as the UI sends it, `items.rs` native items (a line's picture goes through the platform's `menu_picture`), `menu_tracking.rs` holding back a menu sent while one is open, `finish.rs` what each line needs finishing, `status_item.rs` which look the icon shows (the attention dot, the quota bars, and the eyes while the daemon keeps the computer awake, which the UI reports through `set_keep_awake_shown`), `icon.rs` its pictures, `set_icon_visible` showing or hiding the icon (called by `app_settings.rs`, not an IPC command); `macos/` the rich status item (`mod.rs` passes `menu_picture` through, as AppKit tints template pictures itself): `finish.rs` the finishing pass, `menu_tracking.rs` following AppKit's menu tracking, `status_item.rs` the accessible name and the attention dot, `lines.rs` the custom session and meter rows, `openers.rs` the quota openers (the rows that open a quota submenu); `windows.rs` plain items with nothing to finish, single-colour template menu pictures recoloured from their alpha for the menu's theme (`menu_picture`; its `theme` module reads the app mode, `AppsUseLightTheme`, which the popup menu follows, not the taskbar's `SystemUsesLightTheme`, and high contrast) with the last menu rebuilt when the system's `ImmersiveColorSet` setting changes (`WM_SETTINGCHANGE`, `MenuTracking::rebuild`), the app icon in colour with the attention dot as its picture (no quota capsules), the label as the tooltip, the click that opens the menu reported as `tray-menu-opened`, and the menu's modal loop followed through a subclass of tray-icon's window (`WM_ENTERMENULOOP`, `WM_EXITMENULOOP`), so a menu sent while it is open is held back and applied from a timer that `WM_EXITMENULOOP` starts (the chosen item's `WM_COMMAND` is posted as the loop ends, and a timer message waits behind a posted one), which a reopened menu kills. The model carries no agent knowledge: the UI sends each window's and meter's fill colour |
| `src/permissions/`, `src/notification_settings.rs`, `src/configuration_file.rs`, `src/directory_picker.rs`, `src/updater/` | The IPC commands for macOS privacy grants (elsewhere they answer that there are none; `permissions/macos.rs` reads the Screen Recording grant by starting the application's own executable with `--screen-recording-probe`, since a process launched without the grant keeps reading false after it is given), the Notifications settings (macOS: the app's pane; Windows: the Settings page `ms-settings:notifications`, opened with `ShellExecuteW`; Linux a no-op), the configuration file dialogs, the system directory picker, and checking for and installing updates (`mod.rs` the commands, the phases and the manifest address, `macos.rs` installing in place when the download ends and naming the macOS manifests `stable.json` and `beta.json`, `windows.rs` naming the Windows manifests `stable-windows.json` and `beta-windows.json`, downloading only and starting the NSIS installer, which ends the process, from the restart (`install_for_restart`, which the exit flow's `confirm_quit` calls) and, without the relaunch, on every other way out of the application (`exit.rs`); `replaced_on_disk` says whether an update has replaced the files, which only the macOS install does before the restart) |
| `src/system_settings.rs` | macOS only: the one way the shell opens a System Settings pane (`open_system_settings`), and the address tables of the privacy, notification and Login Items panes; `permissions/macos.rs`, `notification_settings.rs` and `launch_at_login/macos.rs` go through it |
| `src/app_settings.rs`, `src/config_dir.rs` | The two settings the shell must know before any page has loaded (run in the background, show the menu bar icon): `settings.json` in the app config directory, read once in `setup` before the tray is created, held in managed state, handed to the page as the window's `settings` query parameter (`current_json`; `recovery.rs` rebuilds it with the current values) and changed by the page through `set_app_settings`, which applies the change to `background.rs` and `tray/` and rewrites the file. `config_dir.rs` is the config directory's path and the atomic JSON write that `app_settings.rs` and `window_state.rs` share |
| `src/window_state.rs`, `src/page_isolation/`, `src/diagnostics.rs` | Remembering and validating the window frame (`initial_window` never fits it below `MIN_SIZE`, so on a screen smaller than that, such as 1024×768, Windows caps the width at the screen's, and the layout stays usable; what the system frame adds around the inner size is `chrome::SystemFrame`); blocking non-image `http(s)` requests in the window's webview, which on macOS is a WebKit content rule list (with a development-only localhost exception) and on Windows a WebView2 `WebResourceRequested` filter installed on the built window (`install`, answering 403; `policy.rs` decides, letting through images, the app's own `tauri.localhost` and `ipc.localhost`, and in debug builds `localhost`), and nothing on Linux; the `diagnostic!` log to stderr and `desktop.log` under `~/.octoboard/logs/`, where the home is `USERPROFILE` on Windows and `HOME` elsewhere, as the daemon reads it |
| `capabilities/default.json`, `permissions/*.toml` | The IPC allowlist and the app-defined permission files it names |
| `tauri.conf.json`, `tauri.macos.conf.json`, `tauri.windows.conf.json`, `windows/installer-hooks.nsh`, `Info.template.plist`, `Entitlements.plist`, `icons/`, `images/`, `licenses/` | Where the window's UI comes from (`index.html` with the window's query, which Tauri resolves against `devUrl` under `tauri dev` and against the bundled assets otherwise), the `octoboardd` `externalBin`, the public key that verifies the update archive (`createUpdaterArtifacts` is off: the scripts make and sign the archive); the base file holds what every target shares, and Tauri merges the file of the target OS over it (arrays replace): `tauri.macos.conf.json` the bundle targets, icons, the generated `.lproj` resources and `bundle.macOS`, `tauri.windows.conf.json` the NSIS target (unsigned, WebView2 through its bootstrapper, per-user install), the `icon.ico` among the icons, the ConPTY files `scripts/fetch-conpty.mjs --installer` lays out under `target/conpty-bundle/` (fetched by the Windows overlay's before-dev and before-build commands) and the Windows Terminal licence texts in [`licenses/windows-terminal/`](../../apps/desktop/src-tauri/licenses/windows-terminal/README.md) as bundle resources, and the updater's passive install mode, and the NSIS installer hooks (`bundle.windows.nsis.installerHooks`, `windows/installer-hooks.nsh`: before the install they end the app and move each shipped file a process still holds aside as `<file>.old-<n>` so the new one can be written, put them back when the install fails, and delete what was moved aside after the install and before the uninstall; the shipped files are listed in the hooks, so one added to `externalBin` or to the Windows resources is added there too, which `apps/desktop/scripts/installer-hooks.test.mjs` checks against both configs; the daemon removes its own leftovers at start, `platform::build_files` in `docs/structure/daemon.md`); bundle metadata (`Info.template.plist`); the entitlements for the privacy grants (Apple Events, camera, audio input, contacts, calendars, photos, location; `Entitlements.plist`, wired by `bundle.macOS.entitlements`); app and tray icons; the DMG background. `icons/icon.ico` is the Windows icon, generated from `icons/icon.png` at 16 to 256 px. `icons/AppIcon.icon/` is the macOS 26 layered icon (an Icon Composer package listed in `bundle.icon`, compiled by Xcode 26's `actool`); its `Assets/octopus.png` is derived by hand from `assets/branding/logo.png` and `icons/tray-template.png` by hand from the app icon, and no script regenerates either |
| `localizations/`, `generated-localizations/`, `Info.plist` | Native permission catalogs (one JSON file per language) and their generated bundle resources; generation belongs to the scripts module below |

### [`scripts/`](../../apps/desktop/scripts/README.md) (`apps/desktop/scripts/`)

The native-resource generation, sidecar build, local build, local install, version preparation, release, update-signing
and release-publishing scripts, with their shared `bundle.mjs`, `update-archive.mjs` (packs and signs the update
archive), the testable `release-manifest.mjs` (which manifests each platform writes, the platform selection and the tag message's `Platforms:` line) and the temporary `actool/` shim. `release.mjs` dispatches on the host to
`release-macos.mjs` or `release-windows.mjs`; `windows-release.mjs` holds the Windows signing modes, the `signtool`
checks and the installer inspection, and `sign-file.mjs` is the per-file sign command of the `command` mode. `release-desktop.mjs` owns the
`release:version` command that prepares and pushes a version for CI (`--platforms` for a version of one platform); `tag-message.mjs` reads a tag message for `.github/release-notes.sh`. `publish-release.mjs` publishes the selected platforms (`--platforms`, both by default). The module README holds the scripts' interfaces,
the automated and manual release procedures, failure recovery, and the rule that the version lives in two places.

## IPC surface

Commands permitted through `capabilities/default.json` and `permissions/*.toml`: the exit flow
(`frontend_exit_heartbeat`, `begin_quit`, `confirm_quit`, `daemon_exit_detail`), `set_menu_labels`, `set_tray_menu`,
`set_app_settings`, `set_keep_awake_shown`, `launch_at_login_status`, `set_launch_at_login`,
`open_login_items_settings`, `reveal_main_window`, `bring_to_front`, `permissions_status`, `request_permission`,
`open_privacy_settings`, `open_notification_settings` (also the Windows notification settings), `save_configuration_file`, `open_configuration_file`,
`pick_directory`, `check_for_update` and `install_update`. Events to the webview: `settings-requested`,
`about-requested`, `tray-session-chosen`, `tray-updates-requested`, `tray-menu-opened`, `exit-requested` and
`daemon-exited`.
`packages/ui/src/platform/tauri.ts` maps commands and events onto the platform adapter's capabilities; it is the UI's
only counterpart of this surface.

## Dependency direction

- The shell depends on the daemon only as a sidecar executable and a handshake line; the UI depends on the shell only
  through the platform adapter. Neither the Rust crate nor the scripts import daemon code.
- `src-tauri/build.rs` reads the repo-root `config/app.json`; the scripts use `scripts/lib/env.mjs` and `scripts/lib/git.mjs` at
  the repository root.

## Where new code goes

- A new native capability the UI needs: a module in `src-tauri/src/`, its command registered in `lib.rs`, a permission
  file in `permissions/` and its entry in `capabilities/default.json`, and the adapter capability in
  `packages/ui/src/platform/`. A difference by OS the UI must know of is a field of `host_facts.rs` and `HostFacts`, not a user-agent
  test. A command that carries daemon data does not belong here.
- Menu bar icon work stays inside `src/tray/`: parse in `model.rs`, build in `items.rs`, pictures in `icon.rs`,
  native-only finishing in `macos/` (`windows.rs` for its counterpart).
- Code that differs by platform goes into the concern's `macos.rs` and `windows.rs` (or its inline `mod macos` and
  `mod windows`) behind the shared surface its `mod.rs` selects, not behind `cfg(target_os)` in shared code. What
  shared code may still carry is no behaviour of its own: the selection of the platform half; a module that exists on
  one platform only (`system_settings.rs`); lint attributes for code a platform does not reach
  (`cfg_attr(..., allow(dead_code))`); `cfg(any(windows, test))` on a pure helper only the Windows half calls, so its
  tests run everywhere; the per-target fact tables of `host_facts.rs`; and a test step for what a platform's file
  system lacks.
- A desktop build or release command belongs in this package's `scripts/` and `package.json`. Build steps share
  `bundle.mjs`; the part of a publishing decision that needs no GitHub goes in `release-manifest.mjs` (which reads only the
  daemon's holder floor from the tree) so it can be tested without it.

## Shared entry points

| Need | Entry point |
|---|---|
| A diagnostic line | the `diagnostic!` macro (`src/diagnostics.rs`) |
| Write a JSON file under the app config directory | `config_dir::write_json` (path from `config_dir::config_path`) |
| A setting the shell must know before the page loads | a field of `AppSettings` in `src/app_settings.rs`, applied in `set_app_settings`; the page side is `createShellPreference` (`packages/ui/src/lifecycle/shellSettings.ts`) |
| Stop the daemon before a restart or quit | `sidecar::stop_daemon` with a `StopKind`: waits for the daemon to exit after the UI's request, then sends `POST /shutdown` (`request_stop` in `sidecar/stop.rs`), or SIGTERM on macOS when the request fails (the platform half of `terminate` in `sidecar/stop.rs`; Windows has no signal), then kills (`TerminateProcess` on Windows); the update restart's `Planned` kind sends `POST /planned-stop` instead (repeated once, never SIGTERM) and waits 30 s (above the time the daemon takes to save the screens in the worst case) for the screens to be saved before it kills, and the user's session ending takes `stop_daemon_at_session_end`, with no wait for the UI and within one time budget (the request included), ending a planned stop that is under way instead of waiting for it. The sidecar is started through the shell plugin, which on Windows gives it a hidden console (`CREATE_NO_WINDOW`) |
| Relaunch, applying a downloaded update | `exit::confirm_quit` with `restart`: under the `installing` guard it shares with `quit_installing` and `install_on_exit`, it stops the daemon with the planned stop (`sidecar::stop_daemon`, `StopKind::Planned`; no quit note) and calls `updater::install_for_restart`, which on Windows starts the held installer with the relaunch, ending the process after saving `window_state` and removing the tray icon, and on macOS does nothing; when it returns, the guard is given back and `app.request_restart()` relaunches |
| End the application, installing a downloaded update | `exit::on_exit_requested` and `exit::on_exit`, which stop the daemon (the ordinary stop) and call `updater::install_on_quit` (Windows; nothing is held on macOS) |
| Open a System Settings pane | `system_settings::open_system_settings` |
| Paths, `tauri build`, bundle checks in a script | `apps/desktop/scripts/bundle.mjs` |
| Pack and sign the update archive (or sign the Windows installer) | `apps/desktop/scripts/update-archive.mjs` |
| Windows code-signing mode, `signtool` checks, installer inspection | `apps/desktop/scripts/windows-release.mjs` |
| Environment files and `git` in a script | `scripts/lib/env.mjs` (`loadEnv`) and `scripts/lib/git.mjs` at the repository root |

Consistency checks that hold structure: `src-tauri/build.rs` (app name, repository, license and the two version values),
`pnpm test` in this package (the release scripts and the update archive), and Rust format, clippy and tests through the repository checks.
`lifecycle::windows::tests::the_desktop_precedes_default_processes_at_session_end` checks the Windows shutdown order.
