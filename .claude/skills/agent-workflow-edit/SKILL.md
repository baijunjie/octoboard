# Editing the workflow

The "Workflow" section between `<!-- setup-agent:workflow:begin -->` and `<!-- setup-agent:workflow:end -->` in the
project instruction file is the only place in the project where the workflow is written: what to call before starting
work and before delivery, in what order, and when to skip. Every edit happens only between that pair of markers, and
the markers themselves are neither deleted nor changed. When the instruction file does not have that pair of markers
yet, stop and ask the user to run the `setup-agent:workflow` installer, then edit the section once it is generated —
do not create it yourself; when the installer does not generate the section (the project has no `agent-docs`,
`agent-unit-test`, or `agent-change-check` installed), tell the user there is nowhere to register the workflow, and do
not create somewhere else.

## Record dispatch only

- Each step records only: when it is done, which skill it is handed to or what command is run, which step it comes
  after, and under what circumstances it is skipped.
- Details of how (how to review, how to write tests, what to write in the docs) belong to the skill responsible for
  them and are not copied in here; to change the how, change that skill.
- Entries in "### This project" must not weaken the general rules at the start of "### Before delivery" (such as
  waiving the self-check or skipping user confirmation).

## Where to edit

- Everything outside the "### This project" subsection is generated by the `setup-agent:workflow` installer from the
  `agent-docs`, `agent-unit-test`, and `agent-change-check` installed in the project, and is rewritten wholesale on
  reinstall; do not write project-specific content there.
- Project-specific steps, ordering, and skip conditions are written only into the "### This project" subsection — do
  not start another section, and do not scatter them elsewhere in the instruction file or into other docs. Anchor each
  entry on the step names above, not on step numbers (numbers shift with the skills installed):
  - "After 'Change check': ..." "At the end of 'Before starting work': ..." — adding a step.
  - "Skip condition for 'Add unit tests': ..." "Move 'Documentation update' before 'Change check'" — changing an
    existing step's skip condition or order.
  - When the step or subsection an anchor sits on is not currently there, ask the user first.
- When writing the first entry, replace the parenthesized placeholder line in the subsection; when every entry is
  deleted, write this placeholder line back:

  ```
  (None yet. Project-specific steps are written here one per entry, anchored on the step names above, e.g. "After 'Static checks': ..." or "Skip condition for 'Static checks': ...".)
  ```
- Other skills and installers must not write workflow content into the instruction file themselves; to register a
  step, edit the "### This project" subsection per this skill.

## Syncing after a skill is added or removed

- What was added or removed is one of `agent-docs`, `agent-unit-test`, `agent-change-check`: stop and ask the user to
  run the `setup-agent:workflow` installer to rebuild everything outside "### This project"; afterwards, change or
  delete the entries in "### This project" anchored on steps that are gone.
- What was added or removed is another dedicated skill: add an entry in "### This project" naming that skill, stating
  whether it belongs before starting work or before delivery, which step it comes after, and when it is skipped;
  for a removal, delete the corresponding entry and fix every other entry that mentions it. When unsure whether it
  belongs in the workflow at all, or at which step, ask the user first.
- Write only the skills currently installed; leave no placeholder for ones that are not.

## What does not belong in this section

Anything about "when to call what, in what order, when to skip" belongs to the workflow; anything about "what to abide
by while working" is a behavioral convention and does not belong in this section — output style (such as Concise+) and
subagent dispatch rules are the latter, are not moved in here, and are not touched when editing the workflow.

## When done

Tell the user which entries were changed; changes to the instruction file must be committed to version control and
take effect in the next session.
