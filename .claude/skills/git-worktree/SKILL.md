# Working a worktree branch

Below, "the branch" means the branch under development in a worktree, and "the target branch" means the branch it merges back into. When unsure, report back: stop, spell out what needs deciding (with the options) or what information is missing, together with what you have already found out, and let the recipient of the report (the user, or the dispatcher passing it on to the user) decide before going on; do not decide for yourself.

Where a branch merges back to and where it was cut from are read from its own git config (see "## Creating" for how they are recorded): if the target branch (`targetBranch`) cannot be read, the fork point (`forkPoint`) is missing, or the named worktree has no branch checked out (a temporary `--detach` worktree), report back in every case — do not guess from the branch name, and do not estimate one yourself to fill the gap.
When no branch is named, use the current worktree's branch; when called from the main working copy, use it if there is exactly one worktree branch, otherwise ask the user.
Aligning with the remote (including the rebase and verification within it), merging, and pushing the target branch all happen in the repository's original directory (called the main working copy below, where the target branch should be checked out); squashing, rebasing the branch, and pre-merge verification happen in the branch's own worktree.

## Flow scripts

The mechanical operations in recording, squashing, moving branches, pushing, and cleanup are done by the `flow-*.sh` scripts under the repository's `.githooks/`. Always run the copy in the main working copy (a worktree freshly cut from the target branch may not have these files yet); every `flow-<name>.sh <args>` written below means:

```bash
sh "$(git worktree list --porcelain | sed -n '1s/^worktree //p')/.githooks/flow-<name>.sh" <args>
```

Exit code 1 means the script stopped: handle the reasons named below as described below, report back on any other reason, and relay the hints in its output to the user rather than carrying them out yourself; on exit code 2, or if the script does not exist, report back.

## Creating

- The target branch is whichever branch the main working copy had checked out when the worktree was created; it need not be the main branch, and the same applies when called from another worktree. If the main working copy is in detached HEAD with no branch checked out, report back rather than guessing. Creating a worktree from a worktree branch is not supported: if the branch checked out in the main working copy itself records a `branch.<it>.targetBranch` (that is, it is itself a worktree branch), report back.
- Name the branch with a `feat/`, `fix/`, `refactor/` or `docs/` prefix according to the kind of change; put the worktree at `.worktrees/<short-branch-name>/` inside the repository, where the short name is the branch name with that prefix stripped (`feat/login-retry` goes at `.worktrees/login-retry/`).
- When injecting code only to verify something temporarily, you may open a separate, branchless temporary worktree instead (`git worktree add --detach`); changes made there are never committed, and the worktree is removed as soon as verification is done.
- Before creating the worktree, check whether the main working copy has `.githooks/revert-gate.py`: if not, treat it as not using the revert gate, and skip this bullet and the pre-merge gate precheck; if it does, install the gate if it is not already installed (its hooks and resident guarded branch configuration live in each clone's own `.git/` and do not travel with the repository):
  - Run this in the root of the main working copy: `git config --get-all revert-gate.branch >/dev/null || sh .githooks/install.sh $(env -u GIT_CONFIG_COUNT -u GIT_CONFIG_PARAMETERS git config core.hooksPath >/dev/null && echo --branches-only)`. If it is already installed this does nothing; if not, it installs from the committed `.githooks/branches`; in a repository where `core.hooksPath` is set in the configuration file (hooks owned by a system such as husky; one given temporarily through `-c` or the `GIT_CONFIG_COUNT` environment variable does not count), it only writes the resident guarded branch configuration (the branches always guarded by the gate, usually the main branch).
  - Tell the user if the command actually performed an install; report back on error rather than handling it yourself.
- After that, create in this order:
  1. Align the target branch per "## Aligning with the remote target branch"; being ahead of the remote (unpushed commits) is normal and needs no action; in a project that merges through PRs, report back first: cutting from here brings those commits into the PR. If it cannot be aligned, report back rather than cutting from the old position.
  2. Create the branch and worktree from the aligned target branch.
  3. Record the target branch and fork point: `flow-record.sh <branch> <target-branch> <target-branch>`.

## Aligning with the remote target branch

- In the main working copy, fetch only the target branch's upstream (`<target-branch>@{u}`): `git fetch <upstream-remote> <upstream-branch>`, where the two are the values of `git config branch.<target-branch>.remote` and `branch.<target-branch>.merge` respectively; there is no need to fetch all branches, which is much slower when there are many branches and tags. A fast-forward or rebase acts on the currently checked-out branch: when one is needed, the main working copy must have the target branch checked out (switch back if it does not; report back if you cannot), and if it has uncommitted changes, report back first. Then handle the relationship between the target branch and its upstream:
  - Behind (no unpushed commits locally): fast-forward with `git merge --ff-only <target-branch>@{u}`.
  - Diverged (unpushed commits locally and new commits on the remote): first record the old position with `git rev-parse <target-branch>` (needed below to move other branches), then `git rebase <target-branch>@{u}` to lift the unpushed local commits on top of the latest remote; resolve conflicts the same way as in "Squashing and rebasing".
    - This rebase brought in new code from the remote, so it must be verified (see "## Merging"); only passing counts as aligned. If it fails, report back that the target branch has been rewritten and the branches have not yet been moved, together with the recorded old position, rather than continuing.
    - Then run `flow-restack.sh <target-branch> <old-position>` to move the branches cut from the pre-rewrite commits onto the new position (a plain rebase would move the pre-rewrite commits a second time).
      It may move other tasks' branches: after the move, tell the user which ones were moved, and before they merge, re-run verification per the "When rebasing a branch again brings in new code" bullet.
      For a reported conflict, ask the user first if it is in a branch other than the one being handled this time; if it has to be resolved, do so in the worktree it names (resolve as in "Squashing and rebasing"), then re-run after `git rebase --continue`; for a reported already-pushed branch, ask the user one by one whether it is exclusively theirs, and if so re-run with `--allow-pushed <branch>`, otherwise report back.
  - No upstream: if exactly one remote has a same-named branch (`<remote>/<target-branch>`), use it in place of the upstream without setting it as the upstream; if several remotes have one, ask the user which to use, then set the upstream with `git branch -u <remote>/<target-branch>`; once settled, run `git fetch <remote> <target-branch>` and handle it as in the two bullets above (with no upstream set, read `<target-branch>@{u}` in them as `<remote>/<target-branch>`); if none has one, skip this.

## Squashing and rebasing

- Squash before merging: every commit on the target branch must be independently explainable and independently revertible. A branch that did one thing is squashed into a single commit; keep several only when it genuinely contains several independent changes, and merge them into one when the split point falls inside a single file. Commit messages describe the final state, not the process (do not write "fix the previous commit" or "adjusted per feedback"), in whatever language the repository's history uses; any `Reverts:` line in the original commits must be carried into the squashed commit, since dropping it turns the revert into an undeclared one.
- Before squashing and rebasing, the branch's worktree must be clean (`git status --porcelain` empty, including untracked files); if it is not, report back rather than committing, stashing, or discarding on the user's behalf: uncommitted changes would get mixed into the commit, wiped out, or hidden in a stash.
- Before starting, record `git rev-parse HEAD` (called the recorded commit below); use it when you need to go back to before the squash.
- To squash into one: write the commit message to a temporary file outside the worktree (such as one created with `mktemp`) and run `flow-squash.sh <target-branch> <file>`; if it reports a declared revert from the original commits that is missing, add it to the commit message and re-run.
- To keep several: split them yourself on the original base `git merge-base HEAD <target-branch>` — with a different base and unmerged content, the old code would count as a new change and silently revert whatever landed on the target branch after that base; after splitting, run `flow-squash.sh --check <target-branch> <recorded-commit>`, and if it does not pass, go back with the command it gives and redo it.
- After squashing, `git rebase <target-branch>`, resolving each commit's conflicts once. Resolving a conflict means combining both sides' changes, not always taking your own side; ask the user when unsure how to combine them. Any further edits needed after the rebase get folded back into the commit they belong to, so that every commit stays independently explainable and independently revertible.
- A branch only you use (no one else's commits on the remote; ask the user when unsure) that has been pushed before is pushed after squashing and rebasing with `flow-push.sh <remote-of-the-branch-upstream> <branch> <upstream-branch-name>` (ask the user where to push if the upstream cannot be read); if it reports that already-pushed history would be rewritten, confirm with the user and re-run with `--force`.
- A branch that has been pushed but is not exclusively yours (the remote has someone else's commits): do not squash, rebase, or force-push it — report back and let the user decide.

## Reverting and undoing

- The repository has a revert gate installed (`.githooks/revert-gate.py`): when a guarded branch moves (each branch's target branch as recorded in `targetBranch`, plus the gate's resident guarded branches), local merge / commit / reset and push are all checked automatically, and updates that rewrite published history or revert changes already on that branch are refused.
- When the gate reports that existing changes were reverted, then unless the revert is deliberate (see the "To genuinely drop a commit" bullet), a squash or conflict resolution went wrong — fix it where the error happened: if it has not yet landed on the target branch, go back to the branch, restore the reverted changes, and fold them back into the original commit (report back first if that means going back to before the squash and redoing it); if a rebase was blocked while aligning with the remote, `git rebase --abort` and rebase again; if it has already landed on the target branch, add a commit in the main working copy to restore it rather than resetting the target branch.
- When a reset is blocked, the index (and, with `--hard`, the working tree too) has already been changed to the target position's content: recover with `git reset --merge` after `--hard`, or `git reset` after `--mixed`.
- To genuinely drop a commit, ask the user first. If it and every commit after it are unpushed, all are to be discarded, no other branch contains them (`git branch --contains <sha>` lists only the target branch), and the main working copy is clean, you may reset them away in the main working copy; if the gate blocks that reset, recover first (`git reset --merge` after `--hard`) and use the approach below instead. In every other case, never use reset or amend on the target branch to remove a commit: once the user agrees, either use `git revert` in the main working copy, or add a `Reverts: <sha>` line to the message of the commit that does the reverting — use either one, and both declare to the gate that the revert is intentional.

## Merging

- Order: align with the remote → squash → rebase → verify (when needed) → confirm with the user → gate precheck → `merge --ff-only` → clean up. Verification means running the project's agreed full set of checks (whichever of format checks, type checking, lint, build, and tests the project has agreed on): it checks the whole current content, including the new code brought in and the places changed while resolving conflicts, not only the original change; if it fails, report back and do not merge.
- Verify the same content only once: squashing, and a rebase that brings in no new code, do not change the content. Skip verifying again only when both of the following hold; when unsure, verify:
  - before squashing, `git rev-parse HEAD^{tree}` is the same as the file tree of the content that passed all checks in this session and was then committed unchanged (moving the branch, resolving conflicts, or further edits all make it differ);
  - before rebasing, `git merge-base --is-ancestor <target-branch> HEAD` holds (after a rebase it always holds, so it must be checked before the rebase).
- Projects that have moved to merging through PRs (as the user has said, or as the repository's docs establish): still align, squash, rebase, and verify when needed, up through confirming with the user; do not raise a PR within this flow, do not merge locally, and do not run the precheck — raising the PR and the cleanup afterward follow the project's PR flow, or the user's instructions where there is none. After aligning and before squashing, if the target branch is ahead of the remote (has unpushed commits), report back first: the branch is rebased onto the local target branch, so those commits will be brought into the PR.
- Before merging locally you must confirm: the main working copy is still on the target branch (switch back if not; report back if uncommitted changes prevent switching back); the branch's `HEAD` is still the commit that was verified and confirmed (if it has been moved, follow the "When rebasing a branch again brings in new code" bullet); the user has confirmed (show them the final commit list and the verification results, stating where earlier verification is reused); and the gate precheck passes (skip this when the main working copy has no `.githooks/revert-gate.py`; when the gate blocks a merge, the main working copy has already been written to the branch's content and needs `git reset --merge` to recover, so precheck first). The gate precheck runs the command below in the main working copy, and counts as passing only when the exit code is 0:

  ```bash
  b=$(git config --get-all revert-gate.branch | head -n1); s=$(git show "refs/heads/$b:.githooks/revert-gate.py" 2>/dev/null) || { echo "gate not ready" >&2; (exit 3); } && python3 -I -c "$s" check <target-branch> <branch>
  ```

  - Exit code 3 (prints "gate not ready"): first install it as in the worktree-creation step; if the first resident guarded branch (the first line of `git config --get-all revert-gate.branch`) has no local branch in this clone, create one with `git branch <that-branch> <remote>/<that-branch>`; re-run, and if it still reports 3, report back rather than treating it as a pass.
  - Exit code 1: it found a problem. If it reports that existing changes were reverted, follow the "When the gate reports that existing changes were reverted" bullet in "## Reverting and undoing" and fix it on the branch; if it reports the target branch as behind or diverged from the remote (as of the last fetch), handle it per "## Aligning with the remote target branch", then go back to the branch, rebase again, and follow the "When rebasing a branch again brings in new code" bullet; for any other reason, report back and relay the hints in its output to the user rather than carrying them out yourself.
  - Exit code 2: the gate itself failed; report back, and do not treat it as a pass.
- Merge locally in the main working copy with `git merge --ff-only <branch>`. On failure, read the output first: if the gate blocked it, the main working copy has already been written to the branch's content, so recover with `git reset --merge` first, then handle it per the "When the gate reports that existing changes were reverted" bullet in "## Reverting and undoing"; if changes in the main working copy blocked it, report back; if it genuinely cannot fast-forward (the target branch has moved again), first align per "## Aligning with the remote target branch", then go back to the branch, rebase again, follow the next bullet through verification and confirmation, re-run the precheck, and merge.
- When rebasing a branch again brings in new code (including branches moved while aligning with the remote), the new code has not been through the earlier verification, so proceed as follows:
  - Re-run verification first (handle a failure as above);
  - once it passes, confirm with the user if the branch's own commit content changed (conflicts resolved, squashed again, and so on) or it has not been confirmed before; if it did not change, reuse the original confirmation;
  - then re-run the precheck and merge.
- After the merge, first go back to the main working copy, then immediately run `flow-cleanup.sh <branch> --merged-into <target-branch>` (it leaves the remote branch alone) — this is part of the merge, no need to ask again.
  - If it reports ignored files in the worktree: when there is anything (such as `.env` or local configuration) beyond dependencies and build artifacts that can be regenerated, ask the user first whether to keep them; if all of it can be deleted, re-run with `--ignored-ok`.
  - For any other reason it reports, report back; do not bypass the script and delete by hand.
- Do not push the target branch automatically; push it only if the user asks.

## Pushing

- When a push of the target branch is rejected (the remote reports non-fast-forward, or pre-push reports the remote has commits you do not have), do not force-push: align per "## Aligning with the remote target branch" and re-push once verification passes.
